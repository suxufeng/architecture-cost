# 第 3 章　服务端边界：一次请求的七种死法

> **章首卡**
> **问题**　接口返回 200，数据却是错的；或者返回超时，其实已经成功。
> **主张**　接口的正确性不在 200，在事务边界、幂等键与超时上。
> **代价**　把这三件事想清楚，每个接口要多花半小时；不想，出问题时要花两周查一个「偶发」。

---

一个扣款接口，测试全过，上线两周后开始出现客诉：用户被扣了两次钱。

查日志：两次请求，间隔 1.2 秒，都返回 200。第一次是用户点的，第二次是客户端超时重试——用户没等到响应，又点了一下。

接口做了幂等：用请求 ID 去重。但客户端每次重试都生成新的请求 ID，所以两次请求在服务端看来是两个完全不同的请求。

再往下查，发现更麻烦的事：第二次扣款发生时，第一次的事务还没提交。

三个问题叠在一起：**事务边界太大**（包了一次外部调用，持锁 1.2 秒）、**幂等键选错了维度**（请求 ID 不是业务 ID）、**超时没有分层**（客户端等 3 秒，服务端要 5 秒）。

这三个问题，没有一个是「代码写错了」。它们都是设计时没被问过的问题。

---

**接口的正确性不在 200，在事务边界、幂等键与超时上。**

## 3.1　事务边界决定并发度

> **你以为**
> 事务越大越安全。把相关的操作都放进一个事务，要么全成要么全败，最稳。

> **实际**
> 事务越大，锁持有越久，并发度越低。一个事务里如果包含一次外部调用（HTTP、RPC、文件上传），那么锁的持有时间就等于那次网络往返的时间——从毫秒变成几百毫秒，并发能力掉两个数量级。

> **机理**
> 数据库的行锁在事务提交时释放。事务里的每一步操作，锁都在。所以事务的长度不是「代码有几行」，是「从第一个写操作到提交，中间隔了多久」。

`公开`　InnoDB 的行锁与事务隔离级别机制见 MySQL 官方文档「InnoDB Locking」与「Transaction Isolation Levels」。

算一遍差距有多大。单行更新，事务耗时 5 毫秒，同一行的写入 QPS 上限约 200。如果在这个事务里加一次 100 毫秒的 RPC，事务耗时变成 105 毫秒，同一行的 QPS 上限降到 10 以下——**并发度掉了一个数量级，而代码只多了一行。**

`推演`　上述算例按「同一行竞争」估算，实际并发还受连接池、隔离级别影响，量级不变。

隔离级别也会放大这个问题。可重复读（RR）下，范围查询会加间隙锁，锁住的不只是存在的行，还有「行与行之间的空隙」；一个看似只读 `SELECT ... FOR UPDATE` 的语句，可能锁住一整段索引区间。读已提交（RC）没有间隙锁，锁的范围小，但会引入幻读，需要应用层处理。

死锁的典型形状：事务 A 先更新账户 1、再更新账户 2；事务 B 先更新账户 2、再更新账户 1。两个事务各持一把锁、等对方那把，数据库检测到之后回滚其中一个。

应用层看到的是「偶发的死锁异常」，重试一次通常就好了。但重试本身又放大了并发——所以治本的办法是**固定加锁顺序**：所有涉及两个账户的操作，都按账户 ID 升序加锁。这样两个事务的加锁顺序一致，就不会交叉等待。

**死锁不是数据库的 bug，是应用没约定顺序。**

选哪个不是「哪个更安全」，是**「你能接受哪种并发异常」**——这和一致性谱系是同一个思路。

更糟的是死锁概率。两个事务各自持有 A 行、等待 B 行，持锁时间越长，撞上的窗口越大。短事务里几乎不会出现的死锁，在长事务里会变成常态。

超时也要分层，否则长事务会被放大。合理的顺序是逐层递减：客户端 3 秒 > 网关 2.5 秒 > 服务端 2 秒 > 下游 1 秒。每一层都比下一层多留一点，保证「上游放弃的时候，下游已经停了」。

反过来——客户端等 3 秒、服务端超时 5 秒——就是上面那个事故的形状：客户端已经重试了，服务端还在跑第一次。**超时配置不是随便填的数字，它决定了「重试会不会变成重复执行」。**

批量操作是另一个容易出问题的地方。一次导入一万条、包在一个事务里，锁会持到全部写完；中间任何一条失败，整批回滚，前面的工作全废。

可行的做法是分批：每 500 条一个事务，失败只回滚这一批，其余继续。**代价是「部分成功」——而这正好是 3.5 要写进坏法表的那一行。**

所以事务边界的设计原则只有一句：**只包住「必须原子」的数据库操作。** 外部调用、消息发送、文件操作，全部移到事务外，用补偿或最终一致处理。

| 操作 | 放事务内 | 放事务外 |
|---|---|---|
| 多条 INSERT / UPDATE | ✓ 必须 | 拆开就不原子了 |
| 唯一性校验（查重） | ✓ 通常要 | 放外面有并发窗口 |
| 调用下游接口 | ✗ 绝不 | ✓ 用 Outbox + 补偿 |
| 发消息 | ✗ | ✓ 本地消息表 |
| 上传文件 | ✗ | ✓ 先传后落库 |

第三行和第四行的处理方式是同一个：**在事务内只写一条「待发送」的记录，事务提交后再由后台任务真正发送。** 这就是 Outbox 模式——它把「跨系统的一致性」换成了「本地事务 + 异步投递」，代价是引入一个后台任务与重试逻辑。

> **判断句**　事务边界不是业务边界，是锁的边界。

> **边栏 · 给管理者**
> **你该问：** 这个事务里，有没有一次网络调用？
> **你可以签：** 「事务内禁止外部调用」写进代码规范，靠静态检查拦。
> **你不该批：** 事务里包着 RPC、还声称「保证强一致」的设计。

## 3.2　幂等键必须是业务维度

> **你以为**
> 幂等就是加个去重：客户端传一个请求 ID，服务端记住处理过的 ID，重复的直接返回上次结果。

> **实际**
> 请求 ID 只能去重「同一次请求的重发」，去重不了「用户点了两次」。因为每次点击都会生成一个新的请求 ID——在服务端看来，这是两个不同的请求。

> **机理**
> 幂等的本质是「同一个业务动作，执行多次等于执行一次」。所以幂等键必须能唯一标识**业务动作**，而不是**传输过程**。

`推演`　本节为语义推演，不涉及具体实现。

三种键的差别，一句话就能说清：

| 键 | 能去重什么 | 去重不了什么 |
|---|---|---|
| 请求 ID（UUID） | 网络重试、超时重发 | 用户重复点击、客户端重试时重新生成 |
| 业务键（订单号 + 操作类型） | 同一笔业务的所有重复请求 | 不同业务但相同参数 |
| 混合键（业务键 + 请求 ID） | 两者都能 | —（但实现更复杂） |

第二行是正确做法。退款接口的幂等键应该是「订单号 + 退款类型」，不是 UUID——因为用户关心的是「这笔订单退了一次还是两次」，不是「这个 HTTP 请求发了几次」。

第三行看起来最全，实际有坑：如果客户端每次重试都换请求 ID，那混合键里的请求 ID 部分会变，去重就退化成业务键。**所以真正的幂等靠的永远是业务键，请求 ID 只是辅助。**

幂等有三种实现，代价不同：

| 实现 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 唯一索引 | 业务键建唯一索引，插入冲突即重复 | 最简单，靠数据库保证 | 冲突抛异常，要捕获并转成「已处理」 |
| 状态机 | 只允许特定状态流转，非法流转直接拒绝 | 语义清晰，能防「跳步」 | 要先设计状态，改流程要改状态机 |
| 预取令牌 | 客户端先取 token，提交时带上，服务端核销 | 能防「提前构造请求」 | 多一次交互，token 要过期 |

第二行在退款场景最合适，因为退款本来就有状态（申请中、已退款、已失败）。第三行适合「提交表单」类场景，代价是用户多点一次「获取凭证」，体验上要藏好。

落地时还有两个细节：

**第一，幂等记录要落库，而且要唯一索引。** 放在 Redis 里、设个过期时间，看起来快，但缓存失效或重启后记录会丢——而重复请求往往就发生在系统不稳定的时候。

**第二，幂等记录要与业务操作在同一个事务里。** 先写幂等记录、再执行业务，中间崩了，就会出现「记录说处理过，实际没处理」；反过来则是「处理了但没记录」，下次重复。幂等记录要留多久，是个容量问题。留太短，超过窗口的重复请求挡不住；留太长，表会无限增长。可行的算法是：**业务重试窗口 × 2**。客户端最多重试三次、间隔 30 秒，那窗口就是 90 秒，留 5 分钟足够；如果是「用户可能隔天再点一次」的场景，就要留 24 小时。

表的增长可以用分区解决：按月分区，删分区而不是删行——**删行会锁表，删分区不会。**

**这两条必须原子。**

> **判断句**　幂等键选业务维度，不是请求维度。

## 3.3　缓存的第一问：不命中时谁扛

> **你以为**
> 加缓存就是提性能。命中率 90%，数据库压力就降到十分之一。

> **实际**
> 命中率的另一面是穿透率。90% 命中意味着 10% 的请求打到数据库——如果总 QPS 是一万，那就是一千。而这一千，可能已经超过数据库的上限。

> **机理**
> 缓存不是「减少请求」，是「把请求挪到另一个地方」。总量没变，只是分成了两份：一份被缓存接住，一份落到数据库。**所以设计缓存的第一问不是「命中率多少」，是「不命中的那一份，谁扛得住吗」。**

`推演`　以下比例为参数化推演，用于说明穿透量的量级。

算一遍。缓存命中率 90%，总 QPS 10,000，落到数据库的是 1,000。数据库单实例的安全上限按 800 算——**已经在超载区间，只是平时被平均值掩盖了。**

更要命的是缓存失效的那一刻。大面积 key 同时过期，命中率从 90% 瞬间掉到 0，10,000 QPS 全部打到数据库。这就是缓存雪崩，而它的触发条件往往是一次批量预热、一次重启、或者一个统一的过期时间。

三种防护，对应三种失效场景：

| 场景 | 现象 | 防护 |
|---|---|---|
| 热点 key 过期 | 单个 key 的请求全打到 DB | 单飞（同一 key 只允许一个请求回源） |
| 大面积同时过期 | 命中率瞬间归零 | 过期时间加随机抖动 |
| 缓存整体不可用 | 全部穿透 | 降级：返回旧值 / 限流 / 熔断 |

第一行的「单飞」是最容易被忽略的。十个并发请求同时发现 key 过期，如果不做单飞，十个都会去查库——而它们查的是同一条数据。单飞的实现很简单：进程内用一个 key 级的互斥，只有第一个请求回源，其余等待结果。

缓存还有两个工程细节，都会在规模上来之后变成事故。

**第一，预热。** 发布重启后缓存是空的，所有请求同时穿透。可行的做法是启动时把热点数据批量加载进去，或者在低峰期发布。没有预热的系统，每次发布都是一次小型雪崩。

**第二，大 key。** 一个 key 存了几 MB 的列表，读取时要序列化整个对象，网络传输与反序列化都慢；更麻烦的是它不可分割，没法分摊到多个节点。**大 key 的解法不是加机器，是拆 key。**

第三行是最后的兜底，也是最少被设计的。缓存挂掉时，系统应该「慢但可用」还是「快但不可用」，这是一个明确的选择，需要提前定：

- **返回旧值**：允许读到过期数据，但服务不中断（适合展示类）
- **限流**：只放一部分请求过去，其余快速失败（适合有明确优先级）
- **熔断**：直接拒绝，让上游降级（适合非核心功能）

缓存与数据库的一致性，也有三种常见做法，各有各的坑：

| 做法 | 顺序 | 风险 |
|---|---|---|
| 先删缓存，再写库 | 删 → 写 | 删完之后、写之前有请求进来，会把旧值重新加载进缓存 |
| 先写库，再删缓存 | 写 → 删 | 极小概率的并发读到旧值，但下次读会修正 |
| 订阅变更日志异步删 | 写 → binlog → 删 | 有延迟，需要接受短暂不一致 |

第二行是工业界最常用的，因为它的风险窗口最小。第一行看起来更「安全」，实际风险更大——**删缓存和写库之间的那个空隙，足够让一个读请求把旧值又塞回去。**

**这三种选择没有对错，只有「你能接受哪种坏」。** 但必须有一个人选，而且写进方案——不选，实际发生的就是「全量穿透，数据库被打死」，那是最坏的一种。

还有一条底线：**缓存与数据库之间要有对账。** 缓存被误改、被脏数据覆盖、或者某次更新失败，都会造成「缓存里的值和库里不一样」——而这种不一致不会报错，只会表现为「用户看到的数据不对，刷新几次又对了」。

对账不需要实时，每天抽样比对一批热点 key 就够。发现不一致时，不要急着「修缓存」，先查它是怎么变的——**不一致本身是症状，原因可能在写入路径。**

> **判断句**　缓存不是加速器，是把流量挪到你看不见的地方。

> **边栏 · 给管理者**
> **你该问：** 缓存全挂的那一刻，数据库会不会被打死？
> **你可以签：** 每个缓存都必须写明「失效时的降级行为」。
> **你不该批：** 只报命中率、不报穿透量与降级方案的缓存设计。

## 3.4　异步是换个地方不一致

> **你以为**
> 异步解耦，提高吞吐。同步调用的问题是耦合，改成消息就解开了。

> **实际**
> 异步没有消除不一致，只是把它从「调用方等待」挪到了「消息传递」——而消息会丢、会重、会乱序。每一样都需要不同的补偿。

> **机理**
> 同步调用的失败是显式的：超时、报错，调用方立刻知道。异步的失败是隐式的：消息发出去了，消费端有没有处理、处理对不对，生产者不知道。

`推演`　本节为失败模式的结构推演。

三种失败，三种补偿，缺一个就会出问题：

| 失败 | 表现 | 补偿 |
|---|---|---|
| 丢 | 消息没到，业务永远不执行 | 本地消息表 + 定时重投 |
| 重 | 消息到了两次，业务执行两次 | 消费端幂等（同 3.2） |
| 乱 | 后发的先到，状态被覆盖 | 版本号 / 时间戳，旧版本丢弃 |

第一行的「丢」最难发现，因为它没有任何报错。生产者认为发出去了，消费者从没收到——中间可能是 broker 重启、队列满了、或者网络闪断。**没有对账的异步系统，丢了也没人知道。**

第二行的「重」是最常见的。至少一次的投递语义意味着重复是常态（第 6 章讲过 QoS 1 的同一件事），所以消费端必须幂等。

举个具体的乱序。订单状态有三条消息：待支付 → 已支付 → 已发货。如果「已发货」先到、「已支付」后到，消费端如果只是「用消息里的状态覆盖当前状态」，订单会从「已发货」退回「已支付」——用户看到已发货的订单又变成待支付。

第三行的「乱」在分区消费时尤其明显。同一个订单的两条消息，可能被分到两个分区、由两个消费者并行处理，到达顺序不确定。解法不是「保证顺序」（代价极高），是**让消息携带版本号，消费端只接受更大的版本**。

还要准备一件事：**积压怎么处理。** 消息堆积有三个常见原因——消费变慢（下游抖动）、生产突增（活动）、消费者挂了。三种的处理方式不同：

- 消费变慢：临时扩容消费者，但受分区数限制，扩不了就只能先降级消费逻辑；
- 生产突增：限流生产者，或者把消息临时转存到另一个队列，事后再消费；
- 消费者挂了：先恢复消费者，再决定是否丢弃过期消息——**很多消息过期就没有意义了，硬消费反而制造错误。**

第三种最需要判断力：一条三小时前的「开门」指令，现在消费还有意义吗？没有。所以队列要配过期时间，而不是「保证每一条都被消费」。

所以异步系统的设计清单是三条：**本地消息表（防丢）、消费幂等（防重）、版本号（防乱）。** 三条都做，才算把一致性挪到了一个能处理的地方。

> **判断句**　异步不是消除不一致，是把不一致挪到你能处理的地方。

## 3.5　写下这个接口最可能的三种坏法

前面四节讲的是四个具体的坑。这一节给一个通用的动作，能在设计阶段就把它们提前抓出来。

**做法**：每设计一个接口，填一张三行的表。

| 坏法 | 表现 | 检测 | 兜底 |
|---|---|---|---|
| 超时 | 客户端放弃，服务端还在执行 | 服务端日志有记录，客户端已断开 | 幂等键 + 结果查询接口 |
| 重复 | 同一业务被执行两次 | 唯一索引冲突 / 幂等记录命中 | 幂等键 + 返回首次结果 |
| 部分成功 | A 成功、B 失败，状态不一致 | 对账任务 / 状态机卡在中间态 | 补偿事务 / 人工介入 |

三行的顺序不是随意的：**超时是第一坏法，因为它同时制造了重复。** 客户端超时后重试，服务端可能已经处理完第一次——所以「超时」和「重复」从来是一起出现的。

第三行「部分成功」最容易被忽略，因为很多人默认「要么全成要么全败」。但在分布式系统里，跨服务的操作本来就是部分成功的：订单创建了、库存扣了、优惠券没发出去。**承认这一点，才会去设计补偿；不承认，就会假设它不会发生。**

不是所有接口都值得填三行。按风险分三级，够用就行：

| 级别 | 接口类型 | 填几行 |
|---|---|---|
| 高 | 涉及资金、权限、不可逆操作 | 三行全填，且要有人评审 |
| 中 | 有状态流转的业务接口 | 至少填「重复」与「部分成功」 |
| 低 | 纯查询、日志上报 | 只填「超时」 |

分级的意义不是省事，是**把评审时间花在会出事的地方**。所有接口都填三行，评审会变成走过场；只有高风险接口填，评审才会真的看。

给一个填好的例子，创建订单接口：

| 坏法 | 表现 | 检测 | 兜底 |
|---|---|---|---|
| 超时 | 客户端 3 秒未收到响应，服务端第 4 秒才提交 | 服务端日志与客户端请求 ID 比对 | 客户端带幂等键重试，服务端返回已有订单 |
| 重复 | 同一用户 1.2 秒内提交两次 | 用户 ID + 商品 + 时间窗 唯一索引 | 第二次返回第一次的订单号 |
| 部分成功 | 订单建成、库存扣减失败 | 订单状态停在「待扣库存」超过 30 秒 | 补偿任务释放订单，或人工介入 |

第三行的时间窗（30 秒）是拍出来的，不是算出来的——**它取决于你能接受「一个订单卡多久」**。这个数应该写在接口文档里，而不是藏在某个定时任务的配置里。

这张表的价值不在于写得多准确，在于**它强迫你在写代码之前想一遍「它会怎么坏」**。想不出来的接口，通常是还没想清楚。

> **判断句**　写不出三种坏法的接口，说明还没设计完。

> **边栏 · 给管理者**
> **你该问：** 这个接口超时之后，客户端重试会发生什么？
> **你可以签：** 接口设计文档必须包含「三种坏法」表。
> **你不该批：** 只写正常流程、不写失败路径的接口文档。

## 决策现场　退款接口退了两笔

`场景`　复合场景，由公开接口设计实践与通用工程经验重构

一个退款接口，上线两周后出现客诉：同一笔订单退了两笔。四条路。

| 选项 | 做法 | 代价 | 放弃什么 | 何时该选 |
|---|---|---|---|---|
| **请求 ID 去重** | 客户端生成 UUID，服务端记 24 小时 | 改动最小 | 用户重复点击的防护 | 只防网络重试 |
| **业务键去重** | 订单号 + 退款类型 做唯一索引 | 要改表结构与调用方 | 灵活性（同一订单不能部分退多次） | 绝大多数退款场景 |
| **状态机** | 退款单有明确状态，重复请求直接返回当前状态 | 要设计状态流转 | 实现简单性 | 流程长、跨系统 |
| **事后对账** | 不拦，靠 T+1 对账发现并冲正 | 不阻断用户 | 当日资金准确性 | 兜底，不能单独用 |

`推演`　表中代价为结构性比较，不含具体实现工时。

**当时不知道的是：** 下游支付渠道的退款接口本身不幂等——同一笔退款请求发两次，渠道会退两次。

这个信息决定了方案的下限。如果下游不幂等，那么「服务端去重」就必须做到百分之百可靠，不能有任何漏网的路径；而如果下游幂等，服务端即使漏一次，也不会造成资损。

**谁拍的板：** 接口方案由服务端负责人拍，资金准确性由财务拍。财务加了一条：**「退款必须可查」——任何一笔退款都要能通过订单号查到它的当前状态和重试次数。** 这一条后来救了命：客诉来时，客服能直接查，不用找研发。

最后落的是业务键去重加状态机：唯一索引挡住重复，状态机保证「已退款」的请求直接返回当前状态、不再触发下游。对账作为兜底保留，但不作为主防线。

**如果重来一次，会改两件事：** 一是先确认下游渠道的幂等性，再定服务端的方案——下游不幂等，服务端就必须做到零漏网，这个前提决定了投入的量级；二是把「可查」写进第一版，而不是等客诉来了才加。

三个月后的数据：拦截的重复请求占总请求的 1.7%，其中大部分是客户端超时重试。这个比例说明——**如果没有幂等，每一百笔退款就有一点七笔是重复的。**

## 代价与边界

**它让接口变复杂。** 幂等表、状态机、对账任务，这些都是「正常流程用不到」的代码。它们只在异常时起作用，平时是纯粹的负担——但异常总会来。

**它把复杂度从「调用方」挪到了「服务端」。** 幂等、状态机、对账，这三样都在服务端，调用方反而更简单了。这是对的——因为服务端只有一份，调用方可能有十个（App、小程序、后台），把复杂度放在唯一的那一侧。

**它假设你能定义「同一个业务动作」。** 「订单号 + 退款类型」这个键，在支持部分退款时就不好用了——同一订单可能退三次，每次金额不同。这时候键要加上金额或退款单号，而这就回到了「业务键怎么设计」这个更难的问题。

**它要求你能看见重复。** 幂等表只有被查到才有价值——如果没有任何监控统计「今天拦下了多少次重复请求」，你就不知道它是真的在起作用，还是只是多了一张表。**一张没人看的幂等表，和维护成本之间没有区别。**

**它在小系统上过度设计。** 内部工具、低频接口，加一套幂等与状态机不划算。判断标准是：**这个接口重复执行一次，会不会造成不可逆的损失？** 会（钱、货、权限），就值得；不会（日志、统计），就不必。

**我判断错过的一次：** 早年我坚持所有写接口都加幂等表，包括一个内部配置管理接口。结果是每次改配置都要多一次写库，而那个接口一天调用不到十次，重复的概率几乎为零。后来把幂等表只留给「涉及钱与货」的接口。教训是：**幂等的成本不在实现，在维护——每多一张表，就多一处要清理的过期数据。**

## 本章栏

**判断句**

1. 锁持有多久，并发就只有多少。
2. 幂等防的是人的手，不是网络的重发。

**本章的代价**

把事务、幂等、超时都想清楚，每个接口要多花半小时；换来的是不用在两周后花两天查一个「偶发重复扣款」。

**不可外包清单**

1. **事务边界不能让 ORM 替你决定。** 框架默认「一个请求一个事务」，而请求里往往不该包那么多东西。
2. **幂等键不能让客户端生成。** 客户端生成的键，只能防它自己的重试，防不住用户的手。
3. **缓存的降级行为不能让运维临时决定。** 缓存挂的那一刻没有时间开会。
