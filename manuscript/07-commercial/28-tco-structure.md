# 第 28 章　TCO 的结构：五段成本，架构决定哪一段

一次设备选型，两家供应商报价：A 报 800 元，B 报 1200 元。

差 400 元一台，一万台就是 400 万。采购的建议很直接：选 A。技术提了两点疑虑——A 的防护等级低一档，A 没有远程升级能力——但都没有被当成硬理由。

理由是「这些都是可以克服的」。防护等级差一档，安装的时候注意点；没有远程升级，派人去现场。

三年后算总账：

| 项 | A | B |
|---|---|---|
| 采购 | 800 | 1200 |
| 部署（调试 + 返工） | 180 | 90 |
| 运营（能耗 + 上门） | 620 | 260 |
| 变更（三次升级） | 340 | 120 |
| 退出（拆除 + 残值） | 160 | 90 |
| **三年合计** | **2100** | **1760** |

`推演`　上表为量级示例，用于说明结构，不代表任何具体产品。

A 便宜 400 元，三年后贵 340 元一台。一万台，就是 340 万——**比当初省下的 400 万，只少了 60 万，而这三年里所有的麻烦都还没算进去。**

**买得便宜是最贵的一种便宜。**

## 28.1　采购价只是五段里的一段

> **你以为**
> 成本就是采购价。报价低的方案更省钱，这是一个不需要讨论的算术。

> **实际**
> 采购价是「获取」这一段的全部，而获取只是 TCO 的五段之一。**它之所以看起来是全部，是因为它是唯一写在合同上的、唯一在当期预算里的、唯一由一个人签字的。**

> **机理**
> 五段成本分散在三年、分散在三个部门、分散在三种预算科目里。**没有任何一个人或一个部门的报表，能看到完整的一列。** 而采购决策，恰恰是由只看第一段的人做的。

五段成本的「可见性」差别很大：

| 段 | 可见性 | 承担部门 | 什么时候发生 |
|---|---|---|---|
| 获取 | 高（合同） | 采购 | 当期 |
| 部署 | 中（项目预算） | 实施 | 三个月内 |
| 运营 | 低（分散在多个科目） | 运维、售后 | 三年持续 |
| 变更 | 低（按需立项） | 研发 | 不定期 |
| 退出 | 极低（没人预算） | 无人 | 三到五年后 |

`推演`　上表的可见性判断为组织实践归纳。

第五行写着「无人」。**拆除、数据迁移、残值处置，通常没有预算科目**——真到那天，从「杂项」里出一笔钱，或者干脆不拆，让它烂在那里。

这也是「买得便宜」能长期成立的原因：**它的代价落在看不见的地方，而且落在这个决策之后很久。**

### 为什么财务报表上看不到五段

有人会问：财务报表不是有完整的成本数据吗？

有，但它按「科目」组织，不按「产品」组织：

| 科目 | 里面混着什么 |
|---|---|
| 主营业务成本 | 采购、制造、部分运费 |
| 销售费用 | 部分部署支持、客户培训 |
| 管理费用 | 部分运维人力 |
| 研发费用 | 变更与升级 |

`推演`　上表为财务报表科目与成本段的对应关系示意。

四行里，每一行都混了两个以上的段。**而 TCO 要的是「按产品、按五段」的切法**——它和会计科目的切法是正交的。

所以这个数只能专门盘一次，不能从报表里直接读出来。**没人做，不是因为难，是它不在任何人的日常工作里。**

### 五段在组织里是分裂的

比「看不见」更麻烦的，是「看到了也不归我管」：

| 段 | 谁负责 | 他的 KPI |
|---|---|---|
| 获取 | 采购 | 单价、交期 |
| 部署 | 实施 | 工期、验收通过率 |
| 运营 | 运维/售后 | 可用性、工单量 |
| 变更 | 研发 | 需求交付速度 |
| 退出 | 无 | — |

`推演`　上表为组织分工的通用形态。

五行五个 KPI，**没有一个人的考核里包含「总成本」**。采购压低单价的功劳是实的，运维承担的上门量是实的，两者之间没有连线。

所以做 TCO 最难的不是算，是**让「多花的钱」和「省下的钱」出现在同一张纸上**——而这张纸通常不存在，因为它的抬头不知道该写谁。

可行的做法很简单：**重大选型时指定一个人出这份五段估算，签上他的名字。** 他不需要为结果负责，但需要为「估过」负责。**有人签字的估算，比没人签字的精确模型有用。**

### TCO 也会被滥用

五段估算有一个反面用法：**把它做成「论证已定方案」的工具。**

方法很简单：把运营段的假设调低（「故障率会逐年下降」），把变更段的次数调少（「预计三年不改」），结论就翻转了。而这些假设看起来都很合理。

识别方法有两个：

- **看假设的依据。** 「故障率会下降」的依据是什么？如果写的是「随着工艺成熟」，那它是愿望；如果写的是「上一代产品第三年的实测数据」，那它是依据。
- **看谁估的。** 五段估算如果是供应商做的，运营段和变更段通常会被低估——**因为这两段的成本由买方承担，供应商没有动机算准。**

所以这份估算应该由买方自己出，或者至少由买方复核。**而复核的重点不是数字，是假设。**

> **判断句**　只看采购价，等于只看成本的五分之一。

## 28.2　五段拆解：每段的驱动因子不同

把五段摊开，每一段的构成与驱动因子都不一样：

| 段 | 主要构成 | 驱动因子 | 架构能改变什么 |
|---|---|---|---|
| 获取 | 设备/许可、认证、首备件 | 单价、认证要求、备件策略 | 选型、集成度 |
| 部署 | 安装、调试、培训、返工 | 环境复杂度、可调试性 | 安装方式、出厂配置 |
| 运营 | 能耗、流量、云资源、上门 | 功耗、通信频次、故障率 | 功耗设计、可服务性 |
| 变更 | 升级、扩容、迁移、改造 | 兼容性、可升级性 | 接口设计、模块化 |
| 退出 | 拆除、数据迁移、残值 | 可拆解性、数据格式 | 结构设计、数据模型 |

`推演`　上表的构成与驱动因子为工程归纳，具体依产品形态。

第二行的「返工」经常被漏算。一个安装说明写得差的设备，返工率能到 15%——**而返工的成本是正常安装的两倍**（要拆、要重装、要重新调试、还要处理客户投诉）。

第三行的「通信频次」是一条容易被忽略的杠杆。**上报频率从一分钟一次改成五分钟一次，流量成本降到五分之一**——而绝大多数业务不需要一分钟的粒度（第 7.6 节讲过按「能省掉哪次上门」筛上报项）。

第四行最能体现「架构决定成本」。**一个没有版本兼容设计的系统，每次升级都是一次小型迁移**；一个接口向后兼容的系统，升级是发个版本就完。

### 段与段之间会互相推

五段不是独立的池子，改动一段，其他段会被推着动。常见的三种推动：

| 改动 | 被推的段 | 方向 |
|---|---|---|
| 提高集成度（减少零件） | 获取 ↓、部署 ↓、运营 ↓ | 三段同向，最理想 |
| 增加功能（加模块） | 获取 ↑、运营 ↑（故障点）、变更 ↑ | 三段同向恶化 |
| 压低单价（换供应商） | 获取 ↓、运营 ↑、退出 ↑ | 反向，最危险 |

`推演`　上表的推动方向为工程归纳。

第一行是少见的「三赢」：集成度提高通常同时降低采购、安装和故障。**「减少零件数」在 DFX 里被反复强调，就是这个道理**（第 21.1 节）。

第二行是「加功能」的真相：功能不是免费的，它的成本会以「故障点」的形式进入运营段。**功能越多、故障面越大，而这条在需求评审时通常不算。**

第三行是这一章反复讲的模式：**单看某一段的优化，往往是别的段的成本转移。**

### 每段怎么估，粗到能定方向就够

TCO 估算不需要精确，需要有量级。五段各有一个可用的粗估方法：

| 段 | 粗估方法 | 数据来源 |
|---|---|---|
| 获取 | 单价 × 数量 + 认证分摊 + 首备件 | 报价单、认证费用 |
| 部署 | 人天 × 人日成本 ×（1 + 返工率） | 历史项目工时 |
| 运营 | 单台年成本 × 年限 × 数量 | 电费、流量费、工单量 |
| 变更 | 每次变更成本 × 预计次数 | 历史变更工时 |
| 退出 | 拆除人天 + 数据迁移 + 残值 | 类比历史项目 |

`推演`　上表的估算方法为工程实践归纳。

第二行的「返工率」是最容易漏的。一个存量改造项目的返工率能到 20%，而它不在任何报价里——**它在「项目超支」这个科目里。**

第四行最难估，因为「预计次数」没有依据。一个可用的替代问法是：**「过去三年，这个品类的产品改过几次？」** 历史频率比拍脑袋准。

第五行最容易被当成零。**拆除、迁移、数据导出，都是真实的人力**——只是它发生在三五年后，没人愿意现在算。

### 每段的驱动因子不同，所以降本要「按段下药」

一个常见的错误是用同一种手段应对所有段：

| 段 | 错误手段 | 正确手段 |
|---|---|---|
| 获取 | 只压单价 | 减少规格过剩、提高集成度 |
| 部署 | 压缩培训时间 | 简化安装、出厂预配置 |
| 运营 | 减少上报（省流量） | 降低故障率、提高远程可达 |
| 变更 | 减少发版次数 | 提高兼容性、模块化 |

第三行的对比最典型：**为了省流量而减少上报，会让故障发现变晚，上门变多**——省的是一段，涨的是另一段（第 7 章算过这个账）。

第四行更隐蔽：**减少发版次数看起来省了成本，实际是把「小步快跑」变成了「大版本跳跃」**——而大版本的风险和迁移成本，远高于多次小版本。

> **判断句**　降本要按段下药，一副药治不了五段。

## 28.3　成本不是加法，是乘法

> **你以为**
> 每个设计选择各影响一笔成本，加起来就是总成本。所以逐项优化，总成本就会下降。

> **实际**
> 一个设计选择通常同时改变三段以上，而且方向可能相反。**逐项优化时看到的是「这项省了」，看不到的是「那两项涨了」。**

> **机理**
> 五段之间不是并列关系，是耦合关系。**同一个技术决定，会被五段分别「收费」一次**——而收费的倍率不同，通常是运营段最贵、获取段最便宜。

三个算例，看清这种「乘法」：

**算例一：降低防护等级。** 外壳从 IP65 降到 IP54，单台省 30 元。但装在潮湿环境的设备故障率上升，上门次数增加，三年运营成本增加约 200 元；同时因为寿命缩短，退出提前两年。

| 段 | 变化 |
|---|---|
| 获取 | −30 |
| 运营 | +200 |
| 退出 | +80（提前更换） |
| 合计 | **+250** |

**算例二：省掉远程通信模组。** 单台省 80 元，省掉年费 15 元。但所有故障都要上门判断，按第 7 章的算式（f×s>c），当故障率超过 3% 时，上门成本就超过了云成本。

| 段 | 变化 |
|---|---|
| 获取 | −80 |
| 运营（上门） | +180 |
| 变更（只能现场升级） | +60 |
| 合计 | **+160** |

**算例三：用专用件替代通用件。** 单台便宜 20 元，但只有一家供应商、停产即断供、二手残值低。

| 段 | 变化 |
|---|---|
| 获取 | −20 |
| 变更（改板 + 重新认证） | +120（一次性，摊到每台） |
| 退出（残值低、难拆解） | +30 |
| 合计 | **+130** |

`推演`　三个算例均为参数化推演，用于说明「一段降、多段涨」的结构，具体数值依产品差异很大。

**算例四：把安装步骤从 20 步简化到 12 步。** 这看起来是「降本」，实际要分两面看：

| 段 | 变化 |
|---|---|
| 获取 | +15（结构调整，模具与零件略贵） |
| 部署 | −60（安装更快、返工更少） |
| 运营 | −20（故障点更少） |
| 合计 | **−65** |

这个算例是反过来的：**获取段涨了，但其余两段降得更多。** 而它在评审时最容易被否决——因为「单价涨了 15 元」是一个可以在会上说的数字，「部署省 60 元」需要有人算过。

**这也是五段思维最难落地的地方：它为「涨价」提供了正当理由，而组织里通常没有人有权限批「涨价」。**

三个算例的共同结构：**省的那一段是「当期、可见、一个人签字」，涨的那几段是「未来、分散、没人签字」。**

这就是为什么「逐项降本」在组织里总是成功、在账上总是失败——**它的成功标准是「当期省了多少」，而它的失败要三年后才结算。**

### 乘法思维怎么落地：一张五行表

不需要复杂模型。每个降本方案附一张表，五行，逐段填「升/降/不变」和量级：

| 段 | 变化 | 量级 | 依据 |
|---|---|---|---|
| 获取 |  |  |  |
| 部署 |  |  |  |
| 运营 |  |  |  |
| 变更 |  |  |  |
| 退出 |  |  |  |

`推演`　上表为降本评估的通用模板。

这张表的作用不是精确，是**强迫填表的人把五段都想一遍**。空着的格子会被追问：「这一段为什么没影响？」——而多数降本方案的隐患，就藏在这些「没想到有影响」的地方。

它还解决了一个沟通问题：**五段填完之后，「省 80 万」和「可能赔 300 万」出现在同一张纸上。** 而在此之前，它们分别在采购报告和售后报告里，永远不会相遇。

> **判断句**　降本省下的钱在当期，多花的钱在未来。

## 28.4　哪一段最大，取决于产品形态

五段的占比不是固定的。产品形态不同，最大的一段完全不同：

| 产品形态 | 最大的一段 | 该优化哪里 |
|---|---|---|
| 硬件设备 | 获取 | 集成度、规格适配 |
| 项目交付 | 部署 | 标准化、预配置 |
| SaaS | 运营 | 资源效率、自动化 |
| 平台型产品 | 变更 | 兼容性、扩展性 |

`推演`　上表的对应关系为工程归纳，具体依业务模式。

第一行是硬件产品的常识，但它有一个反面：**硬件的获取成本占比高，不代表「压单价」是正确动作。** 因为硬件单价压下来的部分，往往会在运营段还回去（28.3 的三个算例）。

第二行最容易被低估。一个项目型业务，部署成本可能占到总成本的一半——**而它的驱动因子是「环境复杂度」，不是「人力效率」**（这笔账怎么算，见第 32 章）。

第三行是 SaaS 的特征。它的边际成本近乎为零，所以「运营效率」直接决定毛利——**而运营效率很大程度由架构决定**：一个每次请求都要查三次数据库的设计，云账单会一直高。

还有一个更常见的错配：**把「部署成本高」当成「实施团队效率低」。**

一个项目型的业务，如果部署成本占到一半，而管理层的第一反应是「加强实施团队考核」，那多半会做错——**因为部署成本的驱动因子是「环境复杂度」，不是「人的努力」。**

同样一批人，换个现场条件，一天的装机量就能差好几倍（第 32 章）。**差的那几倍，不是懒，是环境难度。**

正确的动作是改产品：能不能出厂预配置、能不能免布线、能不能扫码绑定。**这些是设计决定，不是实施决定。**

### 三域的五段，差别在哪

第四行的「变更」最容易被忽略，因为它在早期几乎为零。**平台型产品的成本曲线是后置的**：前两年变更成本很低，第三年开始，每次变更都要考虑几十个存量客户的兼容性。

### 形态会变，占比也会变

五段的占比不是静态的。同一个产品，在不同阶段最大的一段会换：

| 阶段 | 最大的一段 | 为什么 |
|---|---|---|
| 首年 | 获取 + 部署 | 一次性投入集中 |
| 二到三年 | 运营 | 故障与人力开始累积 |
| 三年后 | 变更或退出 | 兼容性、换代压力 |

`推演`　上表的阶段划分为工程归纳。

第二行是很多团队「感觉成本变高了」的原因：**不是成本涨了，是成本的重心从「一次性」移到了「持续性」**。而持续性的支出分散在每个月，不像一次采购那样显眼。

第三行是一次决策点。**三年左右，产品会面临「继续改造还是换代」的选择**——而这个选择的依据，正是五段里「变更」和「退出」两段的估算。**平时不算这两段，到那一天就只能拍脑袋。**

### 优化错段，等于白花钱

一个具体的错配：某团队认为自己「运营成本高」，于是优化了云资源（换了更便宜的机型、调整了实例规格），省了 15%。

但查下来，运营成本的大头是**上门**，不是云资源——云只占运营段的 20%。**优化了 20% 里的 15%，等于总运营成本的 3%。**

正确的动作是反过来的：**先量出五段各占多少，再优化最大的那一段。**

### 怎么量：三个动作，一周能出

量五段占比不需要建模型，三个动作就够：

| 动作 | 做什么 | 产出 |
|---|---|---|
| 一 | 拉一年的实际支出，按五段归类 | 各段的年度金额 |
| 二 | 把一次性投入按年限摊 | 折算成年度 |
| 三 | 算出占比，标出最大的一段 | 优化靶子 |

`推演`　上表为 TCO 盘点的通用步骤。

第一步最难，因为支出分散在多个科目里。「上门成本」可能记在售后费用，「备件」记在存货，「远程模组流量」记在云账单。**把它们按五段归类，本身就需要有人懂业务。**

第二步容易被忽略。一次 100 万的改造投入，按三年摊是每年 33 万——**如果不摊，当年看起来「变更成本爆炸」，实际是一次性的。**

第三步的价值在于「聚焦」：五段里通常有一段占 50% 以上，**优化它就有效，优化其余的加起来也不到一半。**

量这个数不需要精确到个位——一个量级判断就能指导决策。**而多数团队从来没量过，因为五段数据在五个地方，没有人负责把它们拼起来。**

> **边栏 · 给管理者**
> **你该问：** 我们的 TCO，五段各占多少？谁在负责把这个数拼出来？
> **你可以签：** 重大选型必须附一份五段估算，允许误差 30%。
> **你不该批：** 只比单价、不看其余四段的选型报告。

## 28.5　有些成本不能降

> **你以为**
> 所有成本都可以优化。只要有方法，总能找到更省的方案。

> **实际**
> 有三类成本不能降：**可靠性、合规、安全。** 降它们的钱不是省下来，是借来的——**而这三笔债的利息，通常在事故那天一次性还清。**

> **机理**
> 这三类成本的共同特征是「支出确定、收益不确定」。你花钱做冗余，收益是「没有发生的事故」——**而没发生的事故看不见，所以它最容易被砍。**

三个具体形状：

| 类别 | 砍掉什么 | 什么时候还 |
|---|---|---|
| 可靠性 | 去掉冗余、降额不足 | 单点故障那天 |
| 合规 | 跳过认证、简化流程 | 检查或投诉那天 |
| 安全 | 省掉加密、弱化鉴权 | 数据泄露那天 |

`推演`　上表的三类为工程实践归纳。

第一行的账最容易算错。一块冗余电源，成本可能是整机的 8%；而没有它，一次机房断电导致的停服，损失可能是整个季度的利润。**但断电是概率事件，而冗余电源是确定支出**——所以财务上，「砍掉冗余」在当期总是显得正确。

第二行的还债方式很特殊：它不是「赔钱」，是「停下来」。**一个没过认证的产品，不是成本高，是不能卖**——它的损失是「这段时间所有的收入」，而不是「一笔罚款」。

第三行的代价最难量化，也最难辩解。**数据泄露的成本里，最大的一块是信任，而信任不在任何报表上。**

### 「不可降」不等于「不能优化」

三类的支出不能砍，但可以优化——两者的区别是「减少投入」和「提高效率」：

| 类别 | 不能砍什么 | 可以优化什么 |
|---|---|---|
| 可靠性 | 冗余、降额、试验 | 冗余的方式（共享 vs 独立） |
| 合规 | 认证、评估、审计 | 一次做对（减少返工与重测） |
| 安全 | 加密、鉴权、审计日志 | 架构（统一鉴权比逐个实现便宜） |

`推演`　上表的区分为工程实践归纳。

第二行的「一次做对」是最划算的优化。**认证返工一次的成本，通常超过第一次做对的投入**——而这个投入主要是「提前把标准读明白」，不是钱。

第三行的对比很典型：**十个服务各写一套鉴权，和统一一个鉴权网关，成本差三到五倍**，而安全强度后者更高。**这就是「同样的安全目标，架构决定成本」。**

### 怎么判断「这一笔能不能砍」

给一个可用的判断顺序，四问：

1. **砍掉之后，最坏情况是什么？**（不是「可能出问题」，是具体的场景）
2. **最坏情况的概率是多少？**（量级即可）
3. **最坏情况的损失是多少？**（含恢复成本与信任损失）
4. **省下的钱，够不够赔一次？**

第四问是决策现场要用的那把尺子。**如果「省下的钱」小于「一次最坏情况的损失 × 概率」，这笔钱就不该省。**

这个算法有一个陷阱：**概率很低的时候，期望值会显得很小。** 一次十年一遇的事故，按年摊薄，期望损失可能只有省下钱的十分之一——**但它的实际后果是「这一年白干」，而不是「平均每年损失十分之一」。**

所以对「低频高损」的风险，不能用期望值判断，要用**「能不能承受一次」**判断。这是决策现场要展开的事。

### 期望值在低概率下的两个失真

用期望值算「该不该投冗余」，有两个数学上的失真：

| 失真 | 表现 | 后果 |
|---|---|---|
| 概率估不准 | 「十年一遇」通常是猜的 | 期望值可以差十倍 |
| 损失非线性 | 一次事故可能导致客户流失、监管介入 | 平均损失没有意义 |

`推演`　上表的失真为风险决策的通用问题。

第一行的现实是：**没有人知道「十年一遇」是不是真的十年一遇。** 一个新产品的故障率，往往在上市两三年后才有真实数据——而那时候冗余早就砍掉了。

第二行更根本。「平均损失 300 万」这句话，隐含了「可以发生很多次然后平均」——**但很多事故只发生一次，就把业务打没了。** 对这种「不可重复」的风险，期望值这个工具本身不适用。

可行的替代是三条：

- **看「能不能承受一次」**，而不是「平均每年损失多少」；
- **看「恢复要多久」**，而不是「赔多少钱」；
- **看「有没有第二个选择」**，而不是「概率多小」。

第三条最实用。**能承受一次事故的业务，可以砍冗余；不能承受的，冗余不是成本，是营业资格。**

> **边栏 · 给管理者**
> **你该问：** 这块冗余防的是哪一类故障？它防不了哪些？
> **你可以签：** 三类不可降成本（可靠/合规/安全）的支出，不参与降本指标分摊。
> **你不该批：** 用「故障率只有千分之几」论证砍掉冗余的方案——先问这个数是怎么来的。

> **判断句**　砍掉冗余省下的钱，通常在事故那天一次性还回去。

## 决策现场　砍掉一块冗余，省的钱够不够赔

一个产品的电源模块，原设计是双路冗余：主路故障时自动切到备路。单台成本 120 元。

方案评审时有人提出：故障率只有 0.5%，双路冗余「过度设计」，改成单路可以省 120 元一台，一万台就是 120 万。

四个选项：

| 选项 | 做法 | 省下 | 风险 |
|---|---|---|---|
| 一、砍掉冗余 | 全改单路 | 120 万 | 单路故障即停机 |
| 二、保留冗余 | 不改 | 0 | 成本高 |
| 三、分级：关键位置保留 | 30% 的设备保留双路 | 84 万 | 需要定义「关键位置」 |
| 四、砍冗余 + 加监控 | 单路 + 远程告警 | 100 万 | 故障仍会停机，但知道得快 |

选了第三个。

理由不是折中，是**它把「冗余」这个技术手段，换成了「按影响面分配」这个业务判断**：

- 装在小区主出入口、影响上千户的设备，保留双路；
- 装在单元门、影响几十户的，改单路 + 监控。

同一笔钱，用在了影响面最大的那 30% 上。

**谁拍的板：** 技术方案由硬件负责人定，成本与影响面的取舍由产品负责人定。硬件签的是「单路方案的故障率与恢复时间估算」，产品签的是「哪些位置属于关键位置」。

**当时不知道的是：** 0.5% 这个故障率，是实验室数据——它统计的是「电源模块本身失效」，没有算「外部供电异常」。

现场的真实情况是：老旧小区的电压波动比实验室大得多，而且**双路冗余在这种情况下也没用**——因为两路接的是同一个市电。**它防的是「电源模块坏」，防不了「整个小区停电」。**

这个发现让方案又改了一次：关键位置的设备，除了双路冗余，还要加后备电池——**而电池的成本，比双路冗余还高。**

分级的「关键位置」怎么定，也是这次评审的一个产出。三条判据，按优先级：

| 判据 | 含义 |
|---|---|
| 影响户数 | 一个出入口影响多少人 |
| 替代通道 | 这台坏了，有没有别的路走 |
| 恢复时长 | 修好要多久 |

第二条最容易被忽略。**一个影响 50 户但有侧门的设备，实际影响小于一个影响 200 户且唯一通道的设备。** 「影响面」不是只看人数，要看「有没有替代」。

第三条把「可服务性」纳进来了。**一个换模块五分钟的设备，和一个要返厂两周的设备，同样故障率下，停机成本差几十倍。**

还有一个后续：后备电池加装之后，维护成本上来了——电池有寿命，三到五年要换，而换电池需要上门。

这笔成本在当初的评估里完全没有。**它属于「变更」段，而「变更」是五段里最容易被漏的一段**——因为电池更换不像故障维修那样有工单，它是一次计划性的、分散的支出。

后来这件事被写进了产品维护手册：**电池更换作为定期维护项，纳入年度预算。** 一条维护项，让这笔成本从「意外支出」变成了「可预期的运营成本」。

**如果重来一次，会先做一件事：** 把「这个冗余防的是什么」写清楚。**双路冗余防的是「模块失效」，后备电池防的是「供电中断」，两者不是一回事。** 当初的方案里只写了「双路冗余提高可靠性」，没有写它防的具体是哪一类故障——于是评审时所有人都在讨论「要不要冗余」，没有人问「冗余防什么」。

**我判断错过的一次：** 早年我主导过一次降本，把设备外壳的钢板厚度从 1.2mm 降到 1.0mm，单台省 8 元，一年十万台，省 80 万。

两年后批量出现外壳变形——因为设备装在户外，夏天暴晒后钢板变软，加上安装支架的受力点设计本来就紧。返修和更换的成本约 300 万。

那次之后我改了一个做法：**降本方案要附一份「这个改动影响哪一段」的清单**，五段逐一过。外壳变薄这件事，影响的不只是「获取」段，还有「运营」（变形导致的故障）和「退出」（提前更换）。

清单只有五行，但它把「省 80 万」和「可能赔 300 万」放在了同一张纸上。**而多数降本方案之所以能通过，就是因为这两件事从来没被放在同一张纸上。**

`场景`　本决策现场由公开的降本失效案例与冗余设计实践重构，不对应任何具体产品。

## 三域对照：同一笔钱花在哪

互联网、物联网、智能体三个域，五段的占比差别很大。这个差别决定了「钱该花在哪」：

| 域 | 最大的一段 | 最容易被忽略的一段 | 该优先投什么 |
|---|---|---|---|
| 互联网（SaaS） | 运营（云资源 + 人力） | 变更（技术债） | 资源效率、自动化 |
| 物联网（设备） | 获取（硬件） | 部署（安装与返工） | 集成度、可服务性 |
| 智能体 | 运营（推理成本） | 变更（模型与提示词迭代） | 上下文效率、失败重试 |

`推演`　上表的对应关系为工程归纳。

第三行的「运营」有一段特殊结构：**智能体的成本不是按「次」算，是按「每次失败的重试」算**（第 30 章会展开）。一个通过率 80% 的任务，平均要跑 1.25 次才成功，成本是同等工作量的 1.25 倍——**而失败的那些调用，也计费。**

第一行的 SaaS 有一个反直觉之处：**它的获取成本几乎为零，所以「便宜」这个优势在它身上不成立。** 客户选的不是「谁的许可便宜」，是「谁的总成本低」——而总成本的大头在运营和变更。

第二行的「部署」是最容易被低估的。设备类产品的部署成本能占到 TCO 的 20% 到 30%，而它的驱动因子是「环境复杂度」，不是「人力效率」。

> **判断句**　同一笔钱，花在最大那一段才叫降本，花在别处叫挪账。

## 代价与边界

**它要求有人把五段的数据拼起来，而这件事没有天然的责任人。** 采购管第一段，实施管第二段，运维管第三段，研发管第四段，第五段没人管。**所以做 TCO 的第一个动作不是算，是指定一个人。**

**它假设你能估出其余四段。** 新产品的部署、运营、变更成本，只能靠类比和推演。**估算误差 30% 是可以接受的**——因为五段的量级差异通常大于 30%，能分出「哪段最大」就够了。

**它容易被做成「精确的错误」。** 一份精确到元的五年 TCO 模型，看起来专业，实际每个假设都可能错。**更有用的是「五段的相对比例 + 每段的关键假设」**，而不是一个总数。

**它解决不了「没钱」的问题。** 一个现金流紧张的公司，明明知道 B 的 TCO 更低，也只能买 A——**因为 A 的当期支出更低。** 这不是判断错误，是约束。**能做的是把「这个选择多花多少钱」写下来，让它是「一个有记录的妥协」，而不是「一个正确的决定」。**

**它容易被用来「论证已定的方案」。** 五段估算是可以调的：把运营段的假设调低一点，A 就赢了。**防法是把假设单列出来，逐条标注「这是谁估的、依据是什么」**——和第 27 章的 ADR 是同一个思路。

**它容易被「三年」这个期限误导。** 三年是一个常用的 TCO 周期，但产品的实际服役期可能五到八年。**周期定短了，会把「退出」和「后期变更」切掉**——设计缺陷的账单主要就落在这两段。

**它会和「当期利润」冲突，而这个冲突不该由技术判断。** 一份五段估算能说明「B 的三年成本更低」，但决定买 A 的可能是现金流。**技术要做的是把这个代价写清楚，不是替财务做决定。**

**它在小规模上不划算。** 买十台设备，做五段 TCO 分析的时间成本超过省下的钱。**小规模的正确做法是「跟着有经验的人买」**——他的经验里已经包含了他踩过的坑。

## 本章栏

**一页话**

采购价只是五段里的一段，而它是唯一写在合同上、唯一在当期预算里、唯一有人签字的，所以它看起来像全部。五段是获取、部署、运营、变更、退出，每段的驱动因子不同，降本要按段下药。成本不是加法是乘法：一个设计选择同时改变三段以上，省的那段在当期可见，涨的那几段在未来分散。哪段最大取决于产品形态：硬件重获取、项目重部署、SaaS 重运营、平台重变更；优化错段等于白花钱。三类成本不能降：可靠性、合规、安全——砍它们不是省钱，是借钱，而利息在事故那天一次性还清。判断一笔钱能不能砍，四问：最坏情况是什么、概率多大、损失多少、省下的够不够赔一次。

**判断句**

1. 采购价是唯一写在合同上的那一段。
2. 砍冗余省下的钱，事故那天一次性还回去。

**可以立刻做的一件事**

挑一个正在用的系统或设备，把它的成本按五段列一遍，看哪一段最大。

**五个问题（评审时用）**

1. 这个方案的 TCO，五段各占多少？谁估的？
2. 这次降本，影响的是哪几段？涨的那几段算了吗？
3. 我们产品最大的一段是哪段？优化动作落在这一段上了吗？
4. 这块冗余防的是哪一类故障？还有别的故障它防不了吗？
5. 如果最坏情况发生，省下的钱够赔几次？
