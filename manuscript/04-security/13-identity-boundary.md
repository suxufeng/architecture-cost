# 第 13 章　身份与边界：权限给多了才是常态

一个客服人员接到用户电话，说查不到自己的订单。客服打开后台，把订单号后面的数字改了一位，看见了另一个人的订单——姓名、电话、地址、买了什么，全在里面。

这件事没有惊动任何人。客服没有破解密码，没有绕过防火墙，用的是公司发给她的账号、公司自己开发的页面、公司授权的接口。她只是把一个数字从 `10231` 改成了 `10232`。

三个月后做数据安全审计，把访问日志拉出来才发现：这条路径上，任何人只要登录，就能看任何订单。而它在那里已经存在了四年。

这是权限问题最典型的形状：**它不是「被攻破」，是「本来就没关」。**

**绝大多数安全事故不是被攻破，是权限给多了。**

## 13.1　权限只增不减

> **你以为**
> 安全事故是有人突破了防线——猜到了密码、找到了漏洞、绕过了认证。

> **实际**
> 绝大多数是「有权限的人用了不该有的权限」。攻击者往往用的是合法账号、合法接口、合法请求，只是这个账号本来不该有这么大的权限。公开的 Web 应用风险清单里，「权限控制失效」长期排在第一位——不是因为它最难防，是因为它最常见。

> **机理**
> 权限有一个单向棘轮：每次「临时开一下」「方便测试」「先这样上线」，都会沉淀成一条永久记录。而回收权限需要有人记得、有人敢删、有人承担「删了之后业务报错」的责任。开的时候一个人点头就够，删的时候要三个人签字——这个不对称，就是权限膨胀的动力学。

权限膨胀有五种来源，每一种都有具体的现场：

| 来源 | 现场 | 三个月后的样子 |
|---|---|---|
| 应急开通 | 线上出故障，先给个高权限排查 | 故障早修好了，权限还在 |
| 复制权限 | 新人入职，「按老王那样配一份」 | 老王是三年前的老账号，权限早就超配 |
| 默认全开 | 新功能上线，怕影响业务，先全放开 | 没人记得这个开关，默认值成了永久值 |
| 测试遗留 | 测试账号为了方便，加了管理员 | 账号没删，还挂在生产环境 |
| 离职未回收 | 离职流程走完，账号停用，权限没删 | 账号重启后权限全在 |

`场景`　上表五类为公开安全实践中的常见形态，不对应任何单一组织。

五种来源里，**第一种最隐蔽，也最合理**。线上着火的时候，没人会先走完权限审批再救火——这是对的，救火优先。问题在于救完火之后，没有「熄灯」这个动作。所以可行的规则不是「禁止应急开权限」，是**应急开通必须带一个自动到期时间，默认 24 小时**。到期自动收回，需要延长就再申请一次。

这个设计的价值在于：它把「记得回收」这个依赖人的动作，变成了不依赖人的默认行为。

### 怎么找出多余的权限

权限审计最容易做成走过场：拉一张权限清单，让各部门确认，各部门都说「确认无误」。因为没人会主动说「我这个权限其实不该有」。

一个更有效的问法，只问一句：**这个权限如果现在被删掉，谁会立刻报错？**

答得出具体的人，说明这个权限是活的；答不出来，说明它要么没人用，要么用了也没人知道——两种情况下都应该删。删完观察一周，没有报错就是确认。

### 申请理由，是权限的保质期

权限申请单上通常有一栏「申请理由」，绝大多数人写「工作需要」。这个字段被浪费了。

它可以更有用：**要求写清「用来做什么具体的事」，并且这件事的结束时间，就是权限的到期时间。** 「排查 3 号楼门禁故障」是一条好理由，它自带结束条件；「日常运维需要」不是理由，是范围。

更好的做法是把理由变成结构化的：**这次要解决什么问题、预计多久、做完之后还需要吗。** 三个字段，十秒钟填完，但它把「永久」变成了「一段时间」。

这不是流程洁癖。**一条权限如果没有结束条件，它就永远不会结束**——因为结束需要有人主动做决定，而没有人会为一个三年前的权限主动做决定。

这个方法的好处是它绕过了「需不需要」的抽象讨论，直接问「谁在用」。**权限的正当性不在于它当初为什么被授予，在于现在还有没有人依赖它。**

### 三种审计做法，效果差很远

权限审计做过很多轮，效果差别不在工具，在问法。三种常见做法，从弱到强：

| 做法 | 怎么做 | 为什么常常无效 |
|---|---|---|
| 清单确认 | 拉一张表，让各部门签字确认 | 没人会主动说「我这权限不该有」 |
| 使用分析 | 拉访问日志，看哪些权限半年没用过 | 有效，但季节性业务会被误判 |
| 反向验证 | 删掉，看谁报错 | 最准，但要承担短期风险 |

第一行是绝大多数审计的实际形态，也是效果最差的——它把判断责任交给了最没有动机判断的人。

第二行可用，但要注意「半年没用过」不等于「不需要」：季度结算、年度审计、应急演练这类权限，本来就是低频的。判据要按权限的性质分组，不能一刀切。

第三行最准。它的可行版本不是直接删，是**先禁用、观察一周、再删**：禁用期间没有报错，就说明这个权限确实可以走。这个动作要挑低峰期做，并且要提前通知——**因为它一定会让人报错，问题只是报错的是不是真需求。**

还有一条更硬的：**权限的数量要有上限。** 一个人身上的权限条目超过某个数（比如 50 条），说明它不是被设计出来的，是被堆出来的。这时候该做的不是逐条审，是重配——按角色重新给一次，而不是在旧的基础上加减。

> **判断句**　权限的正当性，不在当初为什么给，在现在谁还在用。

## 13.2　换个 ID 还能不能查

> **你以为**
> 接口做了鉴权，登录了才能调，所以是安全的。

> **实际**
> 登录只回答「你是谁」，不回答「你能看哪一条」。这两个问题在工程上是两套机制，而绝大多数漏洞出在第二套——它常常根本没被实现。

> **机理**
> 接口从客户端收到一个对象标识，直接拿它去查库，查到了就返回。整个链路里没有任何一处检查「这个对象属于当前这个人」。这种缺陷有个专门的名字：不安全的直接对象引用。它的特点是——**请求完全合法**。

形状很简单：

```text
GET /api/orders/10232
Authorization: Bearer <她自己的合法 token>

→ 200 OK  {... 另一个人的订单 ...}
```

三种变体，一种比一种隐蔽：

| 变体 | 位置 | 为什么容易被漏 |
|---|---|---|
| 路径参数 | `/orders/10232` | 最明显，也最常被扫出来 |
| 请求体字段 | `{"userId": 5678}` | 看起来像业务参数，不像权限参数 |
| 批量接口 | `{"ids": [10231, 10232, ...]}` | 单条接口校验了，批量接口另写了一套 |

`公开`　不安全的直接对象引用（IDOR）与权限控制失效（Broken Access Control）均为公开的应用安全概念；后者在 OWASP Top 10 2021 版中列为 A01。

### 修法的差别，比漏洞本身重要

同一个漏洞有两种写法，差别不在风格，在「忘不忘得掉」。

第一种，先查再比：

```text
order = SELECT * FROM orders WHERE id = ?
if order.user_id != current_user.id: return 403
```

第二种，把归属写成查询条件：

```text
order = SELECT * FROM orders WHERE id = ? AND user_id = ?
if not order: return 404
```

第二种更好，理由有三条：

**第一，它不依赖「记得写 if」。** 第一种写法里，那个 if 是可以被漏掉的——新加一个接口、复制一段代码、重构时删掉一行，都会漏。第二种写法里，归属条件在 SQL 里，漏了就查不出数据，功能立刻不可用，测试阶段就会发现。

**第二，它让「没权限」和「不存在」返回同一个结果。** 第一种写法返回 403，等于告诉攻击者「这个 ID 存在，只是不是你的」——这是一条有用的信息，可以据此枚举出系统里有多少订单。第二种返回 404，攻击者无法区分。

**第三，它把权限变成了数据边界。** 前者是「应用层判断」，后者是「数据库层过滤」。**能在数据层解决的权限问题，不要留给应用层。**

这条原则可以推广成一句更好记的话：**权限要写在查询里，不要写在 if 里。**

### 越权在日志里长什么样

越权被利用时，日志上通常不是「异常」，而是「太规整」。

三个可检测的形状：

| 形状 | 日志特征 | 说明 |
|---|---|---|
| 顺序枚举 | 同一主体，短时间内请求的 ID 连续递增 | 正常业务很少连续 |
| 越界跳转 | 同一主体访问的 ID 分布跨了多个归属 | 一个人通常只查自己的 |
| 高频重复 | 同一 ID 被反复请求，返回却一致 | 在试探某种条件 |

三个形状都不需要复杂的模型，按主体聚合一次就能算出来。**关键是把「主体」作为日志的一等字段**——很多系统的访问日志只记了接口和耗时，没记「谁」，越权检测就无从做起。

告警阈值不用太灵敏，一条规则就够：同一主体在十分钟内，返回 404 的比例超过 30%，就值得看一眼。正常用户的 404 通常来自失效链接，不会密集出现。

批量接口是第三种变体，也是最常出事的地方。单条接口写了归属条件，批量接口为了性能改成「一次查出来再过滤」，过滤那一步漏了。规则只有一条：**批量接口必须逐条校验，不能用「第一条通过就全通过」。**

### 前端隐藏不是权限

还有一类「看起来做了权限」的实现：把按钮藏起来。

页面上不显示「导出」按钮，只有管理员能看到。这确实是权限的一种表现，但它不是权限本身——**前端代码是发给浏览器的，用户能看到全部。** 打开开发者工具，找到那个被 `display: none` 藏起来的按钮，删掉样式，接口照样能调。

判断方法很直接：**这个操作对应的接口，在服务端有没有独立校验？** 有，前端隐藏只是体验优化；没有，前端隐藏就是一层纸。

同样的道理适用于「接口不公开」：一个没有出现在文档里的接口，不等于不能调。攻击者不看文档，他们看的是前端代码里的请求。

还有一类接口根本没有「对象 ID」，但同样越权：列表接口。`GET /api/orders` 不加任何条件，返回全量。它的修法和上面一样——列表的查询条件里必须带主体，而且这个主体来自 token，不能来自请求参数。

> **判断句**　权限写在查询里，不写在 if 里。

## 13.3　三种粒度

> **你以为**
> 权限粒度越细越安全——能给到「某个字段的某一行」最好，给不到就是设计不到位。

> **实际**
> 粒度越细，维护成本越高；维护成本一旦超过人的承受能力，模型就会被绕过。绕过的方式不是攻击，是「直接给他管理员吧，配起来太麻烦」。

> **机理**
> 权限模型的复杂度有一条隐形上限：**维护它的人能在两分钟内完成一次授予。** 超过这个时间，人会自发寻找捷径，而捷径永远是最宽松的那条。

权限模型有三条主流路线，名字听起来学术，实际对应三种不同的提问方式：

| 模型 | 提问方式 | 典型表达 | 适合什么 |
|---|---|---|---|
| 角色（RBAC） | 你是谁 | 「财务专员可以导出报表」 | 职责稳定、边界清晰 |
| 属性（ABAC） | 满足什么条件 | 「工作时间内、本部门的单子可以审批」 | 依赖运行时条件 |
| 关系（ReBAC） | 你和它是什么关系 | 「文档的协作者可以编辑」 | 权限由对象关系决定 |

`公开`　RBAC 有公开的标准模型（NIST 的 RBAC 参考模型与 INCITS 359 系列）；ReBAC 的公开代表是 Google 的 Zanzibar 论文（2019）。

三条路线的选择，不该按「哪个先进」判断，该按**权限的自然语言描述长什么样**判断：

- 如果能用职位说清——「客服能查订单」——就用角色。
- 如果必须加条件——「客服只能查自己负责的工单，且只能在工作时间」——角色不够，要加属性。
- 如果核心是关系——「这个业主能看这个小区，因为他住在这里」——角色和属性都会变形，该用关系。

关系模型长什么样，值得给个具体的形状。它不存「谁能做什么」，存的是「谁和谁有关系」：

```text
user:zhang  --住户-->  unit:3-201
unit:3-201  --属于-->  building:3
building:3  --属于-->  community:A

规则：community 的管理员，可以读 community 下所有 unit 的通行记录
```

权限不再是查出来的一个字段，是**沿着关系走出来的**。判定的问题是「从主体到客体，有没有一条允许的路径」。

这个模型的好处是它天然匹配组织：楼栋变了、住户搬了，只需要改一条边，不用重配一堆角色。代价是每次判定都要走图，性能要靠缓存顶——这也是为什么公开的 Zanzibar 类实现都把「关系快照 + 一致性令牌」当成核心设计。

第三条最容易被误用。用角色表达关系，会得到一个角色爆炸的结果：每个小区一个角色、每栋楼一个角色，几百个角色，没有人能维护。而关系模型里，它只是「住户—小区」这一条边。

### 粒度不是「越细越好」

功能级、数据级、字段级，三层粒度，成本和收益完全不同：

| 粒度 | 回答什么 | 实现成本 | 常见漏洞 |
|---|---|---|---|
| 功能级 | 能不能用这个功能 | 低 | 有权限就能用全部数据 |
| 数据级 | 能看哪些行 | 中 | 批量接口漏校验 |
| 字段级 | 能看哪些字段 | 高 | 敏感字段未脱敏 |

第三行最容易被跳过。一个接口返回完整的用户对象，里面有手机号、身份证号、住址——有权限看这个用户，不等于有权限看他的身份证号。但在实现上，通常是「一次查出来，整个对象返回」，字段级的权限根本没有落脚点。

可行的做法不是给每个字段配权限，是**在返回之前做一次分级裁剪**：把字段按敏感度分成三档（公开、内部、敏感），不同角色返回不同的投影。这个动作放在序列化层，比放在业务代码里可靠。

**粒度选择的原则只有一句：越接近业务语义越好。** 一个 200 行的权限矩阵，实际能维护的只有 20 行；剩下的会被硬编码，或者在压力下被绕过。**权限模型的复杂度，不能超过维护它的人的认知容量。**

> **边栏 · 给管理者**
> **你该问：** 我们的权限模型里，「角色」有多少个？超过 30 个是谁在维护？
> **你可以签：** 新增角色必须说明「它和已有角色的差别」，不能只写「业务需要」。
> **你不该批：** 为每个客户单独配一套角色的方案——那说明模型选错了。

## 13.4　多层叠加：串联放大，并联取最松

权限校验通常不止一层：网关验一次、服务验一次、数据访问层验一次、下游服务再验一次。看起来是四道防线，实际效果取决于一件事：**这四层用的是不是同一个判据。**

如果是同一个——四层都读 token 里的同一个 `role` 字段，做同一个比较——那它其实只有一层，重复了四次。任何一处判断写错，四层一起错；任何一处被绕过，四层一起被绕过。

**多层的价值不在层数，在判据的独立性。** 网关看「这个 token 有没有权限调这个接口」，服务看「这个主体能不能操作这个对象」，数据层看「这条记录是不是属于这个租户」——三个不同的判据，任何一层漏了，另外两层还能挡。

两种错误形态，名字借用电学：

**串联放大**：每一层都假设「上一层已经校验过了」，于是每一层都只做最宽松的检查。结果是整条链路没有一处真正校验归属。它的特征是——单独看每一层都有代码，合起来等于没有。

**并联取最松**：多个系统各有一套权限，同一个操作可以走多条路径。实际生效的永远是最松的那条。比如后台有严格的权限，但有一个「运维接口」可以直接改数据，而这个接口只校验 IP。

还有一种介于两者之间的做法，近年来很流行：**把鉴权集中到一个网关。**

好处明显：策略集中、不用每个服务各写一遍、改规则只改一处。代价同样明显：**网关不知道业务语义。** 它能看到「这个 token 属于哪个角色」，看不到「这个订单是不是他的」——因为后者需要查业务数据。

所以集中的只能是「功能级」的鉴权，数据级的归属校验必须留在服务里。很多团队上完统一网关之后反而更不安全，原因就在这里：**他们以为鉴权都收走了，服务里的归属校验就慢慢没人写了。**

第二种在组织里更常见，因为它是历史沉积的结果：老系统、新系统、应急脚本、数据同步工具，四条路都能改同一份数据，其中三条没有权限校验。审计的时候看主系统，看不出问题。

### 每经过一跳，权限应该收窄

服务间调用有一个容易被忽略的设计点：A 服务代表用户去调 B 服务，B 拿到的权限应该是多大？

三种做法：

| 做法 | B 看到的身份 | 权限范围 | 风险 |
|---|---|---|---|
| 服务账号 | A 自己 | A 的全部权限 | B 无法区分「A 在调」和「A 代表用户在调」 |
| 透传原 token | 原始用户 | 用户自己的权限 | 权限不衰减，A 能做的事 B 也能做 |
| 派生 token | 原始用户 + 收窄的范围 | 只含本次调用需要的权限 | 实现复杂，要维护派生逻辑 |

第二种是常见做法，但它有一个盲区：**用户对 A 有权限，不代表用户对 B 的某个操作有权限。** 透传之后，B 会按用户的全量权限判断，等于把 A 的授权范围扩到了 B。

第三种是正确形态，代价是要在每次调用时明确「这次只需要什么权限」。这件事在小系统里是负担，在主体多、服务多的系统里是必需——因为**权限不衰减，等于每增加一个下游，攻击面就扩大一圈。**

> **判断句**　多层的价值不在层数，在判据是否独立。

## 13.5　主体扩了三倍：接口、设备、Agent

传统的权限设计只有一个主体：人。现在至少有三类新主体，数量级完全不同。

| 主体 | 数量级 | 身份怎么来 | 主要问题 |
|---|---|---|---|
| 人 | 百到万 | 账号体系 | 权限膨胀、离职未回收 |
| 接口/服务 | 十到百 | 服务账号、证书 | 共享、长期、权限过大 |
| 设备 | 万到百万 | 一机一密、证书 | 数量巨大、物理可接触 |
| Agent | 十到百（增长最快） | 派生凭证 | 工具组合产生新能力 |

四类主体的权限不能放在同一套模型里管，因为它们的生命周期完全不同：人的权限跟着组织变动，服务的权限跟着版本发布，设备的权限跟着安装拆除，Agent 的权限跟着任务创建销毁。

**服务账号最常见的问题是共享。** 一个服务账号被五个微服务共用，日志里看到的都是同一个身份——出了事查不出是哪个服务干的。更严重的是权限：五个服务需要的权限取并集，每个服务都拿到了超出自己需要的部分。

拆分的顺序可以按「爆炸半径」排，不用一次全拆：

| 顺序 | 拆哪个 | 理由 |
|---|---|---|
| 一 | 能改数据、能调外部接口的服务 | 出事影响最大 |
| 二 | 处理个人信息的服务 | 合规要求明确 |
| 三 | 只读服务 | 影响小，可以最后做 |

每拆一个，要同时做三件事：独立身份、独立凭证、独立审计标签。第三件最容易被漏——没有审计标签，拆完还是查不出是谁干的。

规则很简单：**一个服务一个身份，权限取交集不取并集。** 实现上不难，难在改造存量——那些共用账号跑了很多年，拆开要改配置、改证书、改发布流程。

**设备的问题在第 6 章讲过**（一机一密、调试口、吊销），此处只补一句权限侧的话：设备的权限不应该由「它能连上」推导出来，应该由「它被安装在哪、承担什么职责」决定。一台装在单元门口的门禁，它的权限范围就是这个单元——这个信息在安装时是确定的，但很少被写进权限系统。

### Agent 的组合效应

Agent 是四类里最新的一类，也是权限设计最容易出错的一类。

它的特殊之处在于：**风险不在单项权限，在组合。**

给一个智能体两个权限：「查用户资料」和「发站内消息」。单独看，两个都无害——查资料是只读的，发消息是它本来就要做的。组合起来，它获得了「查任意用户并给他发消息」的能力，这是一个骚扰工具。

三个工具，两两组合是三种；五个工具是十种；十个工具是四十五种。**组合数随工具数平方增长，而设计时通常是一个一个批的。**

所以 Agent 的权限不能按「工具」授，要按「数据域」授：

| 授法 | 表达 | 风险 |
|---|---|---|
| 按工具 | 可以用 query_user、send_msg | 组合效应不可见 |
| 按数据域 | 可以读「本小区住户」、可以写「通知」 | 组合后仍在域内 |
| 按任务 | 本次任务只能读这 20 户 | 最严，但每次都要配 |

`公开`　对 LLM 应用「过度代理」的风险，公开的行业清单已单列为一项（OWASP Top 10 for LLM Applications 的 Excessive Agency 条目）。

按数据域授权的价值，在于它把「组合」的爆炸半径框住了：无论怎么组合，它拿不到域外的数据，也写不到域外的位置。

还有一个只有 Agent 才有的问题：**它的权限是动态的。** 传统系统的权限在部署时确定，运行时不改；Agent 会在运行中调用工具、拿到新数据、可能再申请新权限。所以它的凭证必须是短时的、可追溯的、且每次任务结束就失效——这一条在 12.5 讲过凭证三要素，这里补的是「生命周期」：**Agent 的凭证不该比它的任务活得久。**

> **判断句**　Agent 的风险不在单项权限，在工具的组合。

## 13.6　一条权限的四个要素

前面几节讲的是「怎么给、给到多细」。还有一个更基础的问题：**一条权限，到底由什么构成。**

四个要素，缺一不可：

| 要素 | 回答 | 例子 |
|---|---|---|
| 主体 | 谁 | 客服组（角色），不是「张三」 |
| 客体 | 对什么 | 订单（数据域），不是「全部数据」 |
| 动作 | 能做什么 | 读（不含改、不含导出） |
| 条件 | 什么情况下 | 仅限本人工单关联的订单，工作时间内 |

四个要素齐全，这条权限才是可审计的。缺任何一个，它都会在实际运行中变形：

- 缺主体，就变成了「所有人都能」；
- 缺客体，就变成了「全部数据」；
- 缺动作，读写就不分（「有权限」通常意味着全都能）；
- 缺条件，就变成了永久且无条件。

**「管理员权限」不是一条权限，是一堆权限的集合名。** 它的四要素全是空的——主体是「管理员」，客体是「全部」，动作是「全部」，条件是「无条件」。这种集合名在系统里越多，权限就越不可控。

所以设计权限时，一条可用的规则是：**不允许授予集合名，只允许授予具体条目。** 需要批量授予时，由系统展开成条目再授予，而不是直接给一个「管理员」。

### 授予这件事本身，也要有权限

四要素描述的是「一条权限长什么样」，还有一半问题是「谁能把它给出去」。

授予权限是一个高危动作，因为它可以扩大权限本身。三条规则：

- **授予权与业务权分离。** 能批报销的人，不该同时能给自己开权限。
- **不能自我授予。** 系统层面禁止「自己批自己」，这一条要在代码里拦，不能靠制度。
- **授予要有上限。** 一个团队管理员能授出的权限，应该是他自身权限的子集——不能授出自己没有的东西（这条在 12.1 讲过，这里补的是实现：授予时做一次子集判断）。

第三条在实现上常被跳过，因为它要求系统能比较「两个权限集合的包含关系」。但它的价值很高：**它让权限的扩张必须沿着已有的边界走，而不能凭一个管理员账号凭空长出来。**

这条规则的代价是配置量变大。收益是——当有人问「这个账号能做什么」时，你能给出一个确定的列表，而不是一句「他是管理员」。

> **边栏 · 给管理者**
> **你该问：** 现在有多少个账号是「管理员」？名单上一次核对是什么时候？
> **你可以签：** 取消集合名授权，所有授权展开成条目。
> **你不该批：** 以「他是管理员」作为权限说明的审计回复。

### 复核周期要按敏感度分，不能一刀切

权限复核最常见的做法是「每年一次全量复核」，结果就是一次走过场——几千条权限，一周内确认完，没人真的看。

按敏感度分三档，周期不同：

| 档 | 典型权限 | 复核周期 | 复核人 |
|---|---|---|---|
| 高 | 能改数据、能导出个人信息、管理员类 | 每季度 | 业务负责人 + 安全 |
| 中 | 能读业务数据、能发通知 | 每半年 | 直属主管 |
| 低 | 只读公开数据、内部文档 | 每年 | 系统自动（看使用记录） |

分档的价值在于**它把人的注意力集中到了真正危险的地方**。高敏权限的数量通常只占总量的 5%，但这 5% 值得占掉复核精力的 80%。

低敏档交给系统自动处理，判据只有一条：**连续六个月未使用，自动禁用并通知本人**。本人一周内没有异议，就删除。这条自动化规则能消掉大部分僵尸权限，而且不会误伤——真正在用的权限，会有人来认领。

## 决策现场　客服要能查订单，给多大权限

客服团队提出：处理用户咨询时查不到订单，要提工单给技术，一来一回半小时，用户在线等着。要求开查询权限。

四个选项：

| 选项 | 做法 | 客服效率 | 风险 |
|---|---|---|---|
| 一、开全量查询 | 给客服组开订单表的全量只读 | 最高 | 能看到所有用户的订单 |
| 二、提工单代查 | 保持现状，技术代查 | 最低 | 无新增风险 |
| 三、按工单受限查询 | 只能查「当前工单关联用户」的订单 | 中 | 需要改造接口 |
| 四、全量 + 审计 | 开全量，但记录每次查询并告警 | 高 | 依赖事后发现 |

选了第三个。

理由不是它最安全，是**它是唯一一个把权限条件写成数据的方案**——「当前工单关联的用户」是一个可以放进查询条件的字段，不是一句需要人判断的规则。第一和第四都是「给了一片海」，第二是「不给」，只有第三给的是「这一瓢」。

代价很实在：订单查询接口要改造，加一个「工单上下文」参数，服务端据此取用户 ID，再拼进查询条件。改造量约两周，且要改三个调用方。

**谁拍的板：** 效率损失由客服负责人认，数据风险由安全负责人认。两个人在同一份方案上签字，签字的内容不同——客服负责人签的是「两周内客服效率不会改善」，安全负责人签的是「这个接口的归属校验由我复核」。

这个分工很重要：**如果只有安全签字，方案会被拖；如果只有业务签字，条件会被放宽。**

**当时不知道的是：** 受限权限上线后，出现了账号借用。原因是权限按「班组」授予，但排班是轮动的——A 班的人有权限，B 班的人没有，交接时就借用 A 班的账号。三个月后的审计发现，40% 的查询来自三个账号，而这三个账号对应十几个人。

这个问题的根因不在权限粒度，在**权限的授予单位和组织的最小单位不匹配**：权限按班组给，排班按个人轮。修法不是加监控，是把权限改成「按岗位授予 + 随排班自动生效」——人到位，权限到位；人下班，权限收回。

**如果重来一次，会先做一件事：** 在定粒度之前，先确认「权限跟着什么走」——是跟着人、跟着岗位、还是跟着班次。这个问题不确认，粒度设计得再细，都会在组织运行中被绕开。

**我判断错过的一次：** 早年我给一个内部系统设计了很细的权限矩阵，二百多行，每个角色对应一组精确的操作。上线两个月后我发现，运维为了省事，直接给所有人开了管理员。问原因，回答是「配一个人要十分钟，一天来五个新人，我配不过来」。

那次之后我改了两个做法：一是权限模板化（新人入职选一个模板，一键到位），二是把「配权限的耗时」当成一个设计指标——**如果配一次权限超过两分钟，这套模型就会被绕过。** 二百行矩阵本身没错，错在它没有配套的授予效率。

`场景`　本决策现场由公开的权限设计实践与客服工单流程重构，不对应任何单一组织。

## 代价与边界

**它让人变慢，而这是设计目标。** 每一次权限收紧，都会有人说「这样我没法干活」。正确的响应不是放开，是**把申请路径做短**——一键申请、自动审批常见组合、模板化授予。人感受到的摩擦，应该来自「想清楚要什么」，不该来自「走流程」。

**它假设身份是可信的。** 权限设计的前提是「这个 token 确实代表这个人」。身份被冒用（token 泄露、会话劫持、内部人共用账号），后面所有的权限判断都建立在沙子上。所以身份认证的强度要跟权限的敏感度匹配——这一点常被反过来做：核心系统用弱密码，边缘系统反而上了双因子。

**它假设有人看日志。** 权限校验产生的拒绝记录、异常访问记录，如果没有人定期看，等于没有。可行的最低配置是两条告警：同一主体短时间内大量 403（在枚举）、同一主体访问了从未访问过的数据域（在试探）。

**它解决不了「有权限的人主动作恶」。** 权限系统的能力边界是「限制能做什么」，不是「判断该不该做」。一个有合法权限的人，把数据导出去卖掉，所有的权限校验都会通过。这一类只能靠审计、脱敏、水印和制度，不靠权限模型。

**它在极小规模上是过度设计。** 三个人的团队，共用一个账号，风险确实可控——前提是这个账号的所有操作都有日志，且三个人都知道彼此在看什么。规模一到十人，这套做法就必须拆，因为「彼此知道」这个前提消失了。

**它倾向于把安全做成清单。** 权限清单、主体清单、审计清单，做得越全，越容易产生「已经管住了」的错觉。清单只能证明「我们想到了这些」，不能证明「没有别的路径」。真正的验证方式是反过来的：**从一个具体的数据出发，问「有哪几条路能读到它」，然后逐条去关。**

## 本章栏

**一页话**

权限的问题不是「给错了人」，是「给多了之后没人收」。五种膨胀来源里，应急开通最合理也最危险——解法不是禁止，是让它自动到期。越权最常见的形态是换个 ID，修法的关键差别在「权限写在查询里还是写在 if 里」。三种粒度（角色、属性、关系）按业务语义选，不按先进程度选。多层的价值在判据独立，不在层数。主体从人扩到接口、设备、Agent 之后，Agent 的特殊风险是工具组合。一条权限必须写全四个要素，写不全的只是集合名。

**判断句**

1. 权限的数量，比权限的精度更值得先管。
2. 能从数据层挡住的越权，不要交给应用层记得。

**可以立刻做的一件事**

挑一个接口，把「当前登录用户」的 ID 换成别人的，看能不能查到。这个测试不需要工具，改一个数字就行。

**五个问题（评审时用）**

1. 这个接口的归属校验，在 SQL 里还是在 if 里？
2. 批量接口是不是逐条校验？
3. 这类权限现在还有谁在用？删掉会报错的是谁？
4. 服务之间调用的权限，是收窄的还是透传的？
5. Agent 的凭证，比它的任务活得久吗？
