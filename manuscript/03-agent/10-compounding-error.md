# 第 10 章　复利：链路越长越不可靠

> **章首卡**
> **问题**　每一步单独测都能过，端到端只有六成；而且失败之后查不出是哪一步错了。
> **主张**　0.95 的 20 次方是 36%——可靠性靠更短的链路和更多的闸门，不靠更强的模型。
> **代价**　加闸门会牺牲自动化率；不加以，系统会在某个说不清的地方悄悄错。

---

一条十五步的链路：读事件 → 抽字段 → 查上下文 → 补全 → 分类 → 判优先级 → 选模板 → 生成初稿 → 自查 → 修订 → 格式化 → 过一遍规则 → 落库 → 通知 → 归档。

每一步单独测，都能过，准确率大概在 95% 到 97% 之间。团队对这个数字很满意——单步 97%，比人工稳。

上线之后，端到端成功率六成出头。

最麻烦的不是六成。是失败之后查不出是哪一步错的。日志上每一步都返回了正常，输出也都「看起来对」。你能看到最终结果错了，但往前倒推，每一步都像是对的。

有人提议：换个更强的模型。换了，单步从 97% 提到 98%，端到端从 61% 涨到 67%。涨了，但离「能用」还差得远。

---

**0.95 的 20 次方是 36%——链路越长，可靠性的天花板越低。**

---

## 10.1　Demo 是 3 步跑一次，生产是 15 步跑一千次

> **你以为**
> Demo 跑通了，剩下的就是工程化：加个队列、加重试、加监控。逻辑是对的，规模化只是量的问题。

> **实际**
> Demo 通常只有三步，跑一次，输入是你精心挑的。生产是十五步，一天跑一千次，输入是真实的、脏的、带例外的。这两件事之间的差距不是「量」，是**失败概率的累乘**和**例外分支的覆盖**。

> **机理**
> 三个变量同时恶化：
> 1. **步数**：从 3 到 15，每步的成功率要连乘五次以上；
> 2. **次数**：从 1 次到 1,000 次，原本 1% 的小概率事件一天会出现十次；
> 3. **输入分布**：从精选样本到真实数据，长尾部分开始出现——而长尾恰恰是 Demo 从来没跑过的部分。

`推演`　以上为参数化推演，不依赖具体系统。

第三条最容易被低估。Demo 的输入是「典型样本」，生产的输入里有 15% 到 30% 是例外：格式不对、字段缺失、语义歧义、上下文冲突。这些例外在 Demo 里一次都没出现过，所以 Demo 的成功率其实是在**一个被裁剪过的输入分布**上测出来的。

于是出现一种很常见的错觉：单步指标很好，端到端很差，团队认为是「集成问题」，去查接口、查序列化、查超时。查一圈，接口没问题。真正的问题在算术里。

> **判断句**　Demo 的成功率不是成功率的估计，是上限。

## 10.2　复利误差：每一步都对，整条链就是错

> **你以为**
> 每步 95%，就算有几步失败，整体也应该在 90% 左右。最差不过八成。

> **实际**
> 概率不是相加，是相乘。五步 95% 是 77%，十步是 60%，二十步是 36%。而且相乘之后，误差还会互相污染——上游错了一点，下游会在错的基础上继续「正确地」处理，最后得到一个完全自洽、但整体错误的输出。

> **机理**
> 端到端成功率 ≈ 单步成功率 ^ 步数。这个公式简单到不像需要解释，但它在实践里几乎从不被提前算一遍。

| 单步准确率 | 5 步 | 10 步 | 20 步 | 50 步 |
|---|---|---|---|---|
| 99% | 95.1% | 90.4% | 81.8% | 60.5% |
| 97% | 85.9% | 73.7% | 54.4% | 21.8% |
| 95% | 77.4% | 59.9% | **35.8%** | 7.7% |
| 90% | 59.0% | 34.9% | 12.2% | 0.5% |
| 85% | 44.4% | 19.7% | 3.9% | ≈0 |

`推演`　上表为幂函数直接计算，未考虑重试与人工兜底；加入兜底后曲线会上移，但形状不变。

这张表最有用的一行是 95%：**二十步只剩三分之一。** 而「95% 单步准确率」在很多团队里已经算是不错的成绩。

再看一眼 99% 那一行：五十步只剩 60%。这意味着即使你把每一步做到 99%，只要链路足够长，端到端仍然会跌到六成——和开头那条十五步、单步 97% 的链路差不多的水平。**所以「换个更强的模型把单步提上去」这条路，天花板是算术决定的，不是模型决定的。**

比相乘更麻烦的是**误差污染**。举一个例子：第三步「补全」把「朝阳区」补成了「朝阳」；第五步「分类」基于「朝阳」判成了某个类别；第七步「选模板」按那个类别选了模板；后面每一步都在这个基础上「正确地」处理。最后输出一份内部完全自洽、但整体错误的结果。你从最终输出往前倒推，每一步的输入输出都符合各自的规则——因为规则本来就不检查「朝阳」是不是「朝阳区」。

> **边栏 · 给管理者**
> **你该问：** 这条链有多少步？端到端成功率测过吗？
> **你可以签：** 把「端到端成功率」写进验收指标，替代「单步准确率」。
> **你不该批：** 只报单步指标、不报端到端指标的智能体项目。

## 10.3　五层塌陷：诊断自上而下，修补自下而上

链路长只是表象。真正让一个智能体项目塌掉的，通常是五层里的一层先塌，然后带着下面几层一起塌。

| 层 | 塌的样子 | 典型症状 |
|---|---|---|
| **L1 价值层** | 问题选错：这件事本来不该用智能体做 | 做完发现没人用，或者用了还不如原来 |
| **L2 结构层** | 流程没重写：把旧流程原样搬上来，只是中间换了个模型 | 端到端周期没变，只有某一步快了 |
| **L3 算术层** | 复利误差：链路太长，单步再准也撑不住 | 单步指标好，端到端差，且查不出哪步错 |
| **L4 知识层** | 地基是空的：模型需要的知识从来没被写下来 | 答不出来时它不承认，而是编一个 |
| **L5 组织层** | 没人真正拥有它：部署方和结果方是两个部门 | 上线后没人管，指标没人看，坏了没人修 |

`推演`　五层模型为作者方法论，用于定位问题层级，不构成因果证明。

这张表最有用的地方是它给了一个**诊断顺序**：自上而下。

因为下层的问题经常是上层问题的症状。端到端成功率低（看起来是 L3），可能真实原因是流程没重写（L2）——旧流程里有三次人工审批，你把它原样搬进链路，等于在链路中间插了三段「等待」，每段都可能超时。你以为是算术问题，去优化步数，其实该做的是删掉那三段。

反过来，**修补顺序是自下而上**。L5 没人拥有，你修 L1 到 L4 都白搭——上线三个月后没人维护，什么都会退化。L4 知识是空的，你把链路压到五步也没用——它还是会编。

这两个顺序不一致，是很多团队反复返工的根源：他们用「修补顺序」去诊断，从最底层开始查，查了两周发现是上层选错了题。

> **判断句**　诊断自上而下，修补自下而上——顺序反了，会在错误的层级上花掉大部分时间。

## 10.4　三条对策，以及它们各自的代价

复利误差不能消灭，只能对冲。三条对策，每条都有明确代价。

### 对策一：缩短链路 + 设闸门

**做法**：能合并的步骤合并，能删的步骤删掉；同时在链路里插人工确认点——每 3 到 5 步一处，不可逆动作（写库、发消息、付款）前必须拦一道。

**效果**：十五步压到八步，单步 97% 不变，端到端从 63% 提到 78%。

**代价**：**牺牲自动化率。** 每加一道人工确认，就有一批任务停在等人。按每天一千次、每次等五分钟算，等于每天有 83 小时的人工在队列里排着——这还不算等人期间的上下文失效。

`推演`　上述折算为参数化推演，用于说明量级，不代表任何具体业务。

**判断标准**：不可逆动作必须拦，可逆动作可以不拦。写库之前拦，查库不用拦；发消息之前拦，读消息不用拦。

### 对策二：每步做结构化校验

**做法**：上游输出必须过 schema 校验才能进入下一步。字段类型、必填项、取值范围、枚举合法性，都校验。

**效果**：错误就地暴露，不再向下污染。原本要到第十步才发现的错，在第三步就报出来。

**代价**：**工程复杂度上升，且会误伤。** schema 写严了，合法的长尾输出会被判为非法；写松了，等于没写。而且每加一个字段，schema 就要改一处，链路越长，维护成本越高。

**判断标准**：只校验**下游真正依赖**的字段，不要校验「看起来应该有」的字段。下游不用的字段校验它，纯属给自己找麻烦。

### 对策三：隔离上下文

**做法**：只传必要的上下文，不把全量历史往下带。

**效果**：抑制「自我条件化」——模型看到前面自己写过的内容，会倾向于延续它，包括延续它的错误。

**代价**：**需要设计状态层。** 不能靠「把窗口塞满」这种省事的做法，得显式定义：这一步需要哪些字段、从哪来、什么时候失效。这是一次真正的架构工作，不是调参。

`公开`　上下文窗口与状态外置的讨论见公开的 Agent 架构研究；本节不引用具体产品参数。`[待核: 具体论文与年份]`

三条对策里，**第一条最有效，第二条最便宜，第三条最难但最持久**。实践中常见的错误是先做第三条——因为它听起来最「技术」，而且不需要改流程。做完发现没效果，因为复利误差的主要来源是步数，不是上下文。

> **边栏 · 给管理者**
> **你该问：** 这条链里，哪几步是「不可逆动作」？
> **你可以签：** 不可逆动作前强制人工确认。
> **你不该批：** 「全自动、零人工」这个目标本身——它通常意味着闸门被拿掉了。

## 10.5　单步评测冒充系统评测

> **你以为**
> 每个模块的单测都过了，系统就是可用的。评测覆盖率上去了，质量就有保障。

> **实际**
> 单步评测测的是「这个模块在给定输入下的输出对不对」，系统评测测的是「这条链在真实输入下能不能交付」。两者之间隔着交接、状态、时序——而这三样，单步评测一个都不覆盖。

> **机理**
> 一个具体的例子：每个 Agent 单独测都是 95%，但 A 的输出格式在传给 B 时被截断了（长度限制），B 收到一个不完整的输入，按照自己的规则「合理地」补全，然后继续往下。单步评测里，A 的输入是完整的，B 的输入也是完整的，这个截断永远不出现。

`引用`　多智能体系统在生产环境的失败率，公开研究报告给出的区间跨度很大（从四成到八成以上），差异主要来自任务类型与失败定义。本节只取「区间很宽」这个结论，不引用具体数值。`[待核: 机构、年份、样本]`

所以评测要分两层，缺一层都不算数：

- **单步层**：每个模块在标准输入下的准确率。用于定位「哪个模块退化了」。
- **端到端层**：一整套真实任务集（golden set），从输入到交付，全链路跑。用于回答「这次发布能不能上」。

第二层的难点不在跑，在**维护**。任务集要有人负责、要定期更新、要覆盖新出现的例外分支。没有维护的任务集会迅速退化成一堆过时的用例，跑出来的通过率很好看，但和真实分布脱节。

> **判断句**　单步评测回答「模块对不对」，端到端评测回答「这条链能不能交付」。前者不能替后者签字。

## 10.6　上下文不是记忆

> **你以为**
> 上下文窗口够大，把历史都塞进去，它就能记住。窗口从 8K 涨到 128K，记忆问题就解决了。

> **实际**
> 把窗口塞满，得到的不是记忆，是**更长的提示**。它让模型看到更多信息，但不保证它用对了；而且历史越长，早期约束越容易被稀释——跑到第十步，它忘了第二步定下的规则。

> **机理**
> 记忆需要三件事，窗口只能提供第一件：
> 1. **可得**（信息在上下文里）——窗口能给；
> 2. **可检索**（需要时能找到正确的那一条）——窗口不能，得靠索引与召回；
> 3. **可失效**（过期信息要能被标记作废）——窗口更不能，它只会越来越长。

`公开`　分层记忆与状态外置的公开讨论见 Agent 架构研究。`[待核: 具体来源]`

所以正确的做法是**状态外置**：把跨步骤、跨会话需要的东西写进一个显式的状态层，每一步按需读取，而不是靠「它还记不记得」。状态层要能回答三个问题：这个字段现在是什么、谁改的、什么时候失效。

这一步听起来像工程细节，其实是架构决策：**它决定了这条链路能不能被调试。** 状态在窗口里，出错时你只能看到一段自然语言；状态在外部存储里，出错时你能 diff 两个版本。

## 10.7　规格歧义：单 Agent 会追问，多 Agent 只会各自猜

> **你以为**
> 任务描述写得差不多就行，模型很聪明，能理解意图。多 Agent 分工明确，各干各的。

> **实际**
> 单 Agent 遇到歧义会追问——这是它的优点。多 Agent 遇到歧义不会追问，因为追问要跨 Agent 传话，成本太高，于是各自按自己的理解往下做，最后拼出一个内部矛盾的结果。

> **机理**
> 规格歧义是隐性的：写的人觉得很清楚，读的人各有一半理解。单 Agent 场景下，这个歧义在一次对话里被消解；多 Agent 场景下，它被复制成了 N 份不同的理解，然后在集成点爆炸。

`引用`　公开研究把「任务规格问题」列为多智能体失败的主要来源之一（占比区间在三到五成），具体数值随任务类型差异很大。`[待核: 机构、年份、样本]`

对策不是「写得更详细」，是**把歧义显性化**：在任务描述里强制列出「本任务不包含什么」「遇到 X 情况时该问谁」。这两句比写三段背景有用。

> **判断句**　多 Agent 不会追问，只会各自猜——规格里的每一处歧义，都会被复制成 N 份不同的理解。

## 决策现场　要不要把十五步压成八步

`场景`　复合场景，由公开标准条款与通用工程实践重构

一条十五步的链路，端到端成功率 63%，单步 97%。业务要求到 85%。团队提了四个方案。

| 方案 | 做法 | 代价 | 放弃什么 |
|---|---|---|---|
| **合并相邻步骤** | 把「抽字段 + 补全」合成一步，「自查 + 修订」合成一步，十五步变八步 | 单步任务变复杂，单步准确率会下降；合并后的一步要做两件事，出错时更难定位 | 可观测性；合并步骤的内部状态 |
| **删掉校验步骤** | 去掉两条「自查」「规则校验」，直接往下走 | 端到端速度提升明显，但错误不再被拦截，会一路污染到输出 | 错误拦截能力；后续排查成本上升 |
| **减少人工确认** | 三处确认减到一处 | 自动化率提升，但不可逆动作失去拦截 | 风险控制；一旦出事，责任归属不清 |
| **不动链路，换模型** | 单步从 97% 提到 98% | 成本上升；端到端从 63% 提到 67%，仍不到 85% | 预算；而且天花板很快到 |

**当时不知道的是：** 合并之后，单步准确率会掉多少。

这是个关键的量——如果「抽字段 + 补全」合并后单步从 97% 掉到 90%，那么八步 90% 的端到端是 43%，比原来的 63% 还差。合并链路不是免费的：**步数减少的收益，可能被单步准确率的下降吃掉，甚至倒挂。**

所以正确的动作不是先合并，是先测：拿两百条真实样本，分别跑「合并前」和「合并后」，比端到端的数。这个测试两天能做完，比在会上争两周有用。

最后选了「合并 + 保留全部闸门」：八步，三处人工确认一处不减。端到端从 63% 到 78%，没到 85%，但业务接受了——因为那 7 个点的差距被证明来自 L4（知识层是空的），不是链路的错。

> 本场景由公开的 Agent 失败分析与通用工程实践重构，不对应任何单一项目。

## 代价与边界

这套「短链路 + 多闸门」的做法有明确的成本。

**它会降低能力上限。** 链路越短，能做的事越少。把十五步压到八步，意味着放弃了一部分精细处理——某些需要多轮打磨的任务，压短之后质量会下降。所以「短链路」不是普适原则，它适用于**成功率优先**的场景；在**质量优先**且可人工复核的场景里，长链路加人工把关反而更好。

**闸门会被人绕过。** 上线三个月后，业务会开始抱怨「每次都要点一下」，然后有人提议「加个批量确认」，再后来「加个自动确认开关」。闸门一旦可以配置关闭，它就等于不存在。**闸门的有效性取决于它不可配置**——这条很硬，但必须守。

**推演依赖假设。** 本章所有数字都是幂函数推演，前提是「各步失败相互独立」。真实系统里，失败往往是相关的（同一个模型、同一批数据、同一种输入分布），这时候实际成功率会比推演更低，不会更高。所以推演算出来的是**上限**，不是预期值。

**我判断错过的一次：** 我曾经认定「链路越短越好」，把一个十二步的流程硬压到五步。结果是端到端成功率没升反降——因为被合并掉的那几步里，有一步是「人工抽检」。抽检不是浪费，它是当时唯一能发现系统性偏差的环节。压掉之后，偏差照样存在，只是没人发现了。教训是：**压缩链路之前，先分清哪些步骤是「处理」，哪些是「观测」。处理可以合并，观测不能。**

## 本章栏

**判断句**

1. 0.95 的 20 次方是 36%——链路越长，可靠性的天花板越低。
2. 多 Agent 不会追问，只会各自猜——规格里的每一处歧义，都会被复制成 N 份不同的理解。

**本章的代价**

短链路与多闸门会牺牲自动化率和能力上限；换来的是可交付性。在质量优先、可人工复核的场景里，这个交换不划算——长链路配人工把关反而更合适。

**不可外包清单**

1. **链路步数与闸门位置，不能让框架替你定。** 框架默认的编排结构是为了通用，不是为了你的失败代价分布。
2. **端到端任务集，不能让供应商提供。** 他提供的一定是他擅长的场景。
3. **「哪一步错了」的判断，不能让日志替你下。** 日志记录的是每步的输入输出，不记录「这一步的假设是否还成立」。
