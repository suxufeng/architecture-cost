# 《架构的代价》案例来源与引用规范 V0.3

> 全书不写任何公司实际情况 · 三类来源 · 四种证据标签
> 2026-11-06 · 苏煦烽

---

## 1. 一条总原则

> **书里不出现任何公司实际情况。** 不写自家产品、不写自家数据、不写自家制度、不写自家客户与供应商、不写自家口径冲突。

判断标准不是「脱敏够不够」，而是：**这段话会不会让人反推出某家公司的内部情况？** 会，就删，不做改写。

这条原则带来一个直接后果，必须写在最前面：**全书的立论方式变了。** 原来靠一手数据说话，现在靠公开证据与结构推演说话。硬度降一档，风险归零。

| 项 | 旧口径（作废） | 现行口径 |
|---|---|---|
| 证据主体 | 公司内部数据，脱敏后使用 | 公开标准、公开事故、公开研究，可被读者自行核对 |
| 案例形态 | 真实项目，改名字 | 复合场景，明确标注构造方式 |
| 说服方式 | 「我们踩过」 | 「标准这么写、事故这么发生、推演是这个结果」 |
| 最大风险 | 被反推、被内部质疑 | 被说「没干货」 |
| 应对 | 脱敏 | 推演要够硬：给参数、给假设、给推翻条件 |

## 2. 三类来源与写法

| 级别 | 来源 | 能承担什么 | 不能承担什么 |
|---|---|---|---|
| **A 级** | 公开标准与法规（ISO / IEC / GB / 部门规章）、监管公告、上市公司披露、公开事故报告 | 作为论断的**骨架与边界**：标准怎么规定、前提是什么、越界会怎样 | 不能用来证明「企业普遍如此」，标准只说明「应该怎样」 |
| **B 级** | 复合场景（由多个公开案例与通用实践重构） | 作为每章**引子与决策现场**：让读者看见取舍，而不是看见数据 | 不能标注任何真实主体；不能出现可定位的数字组合 |
| **C 级** | 设计推演（给定参数，推导结果） | 作为**机理段的计算**：容量、重试放大、复利误差、成本量级 | 不能写成「我们发现」；必须列假设与推翻条件 |

### 搭配规则（每章固定配方）

**1 个 B 级引子 + 2–3 个 A 级骨架 + 1–2 个 C 级推演 + 1 个 B 级决策现场。**

只有 A 级会像标准解读；只有 B 级会像故事会；只有 C 级会像习题集。三者按这个比例配，才既站得住又读得下去。

## 3. 复合场景构造规范

复合场景是全书唯一允许的「类案例」形态。它必须同时满足五条，缺一条就不能用。

| # | 要求 | 具体做法 |
|---|---|---|
| 1 | 至少糅三个来源 | 一个公开事故 + 一个公开标准条款 + 一个通用工程实践。少于三个就是改名字，不是复合 |
| 2 | 必须标注 | 章末或场景末固定句式：「本场景由 N 个公开案例与通用实践重构，不对应任何单一项目」 |
| 3 | 不出现可定位信息 | 不写城市、规模、时间、型号、金额、机构名的**任意两项组合**——两项齐全即可被定位 |
| 4 | 必须含一个「当时不知道」 | 决策现场的核心是信息不足下的取舍，不是事后英明。没有这一句，场景就退回成故事 |
| 5 | 必须能对应到公开依据 | 场景里每一个技术判断，都要能在 A 级来源里找到对应条款或公开案例 |

**合格与不合格的差别**

- 不合格：「某物业企业的门禁项目，N 千台设备，通过率 95.8%，失败集中在两个批次。」——这是真实项目换了个名字，数字本身仍是内部数据。
- 合格：「一次批量交付验收，抽样方案按 AQL 0.65 判接收；三个月后现场集中出现同一类故障，且集中在两个到货批次。复盘时发现：抽样方案的前提是连续批与稳定生产，而这两条在当时都不成立。」——三个来源糅合，指向标准前提，无任何可定位信息。

## 4. 四种证据标签

| 标签 | 用在哪 | 必须附带 | 典型误用 |
|---|---|---|---|
| `公开` | 标准条款、法规条文、监管公告、公开事故报告 | 标准号 / 条款号 / 发布主体与日期 | 把「行业普遍」当成公开事实 |
| `引用` | 研究报告、第三方统计、媒体调查 | 机构 + 年份 + 样本量 | 海外结论直接当中国结论 |
| `推演` | 容量、成本、误差复利、失效放大 | 假设清单 + 推翻条件 | 推演写成「实测表明」 |
| `场景` | 复合场景（引子与决策现场） | 「由 N 个公开案例重构」一句 | 标了场景却写了可定位信息 |

> 「实测」「设计态」两个标签已取消：前者依赖内部数据，后者依赖自家方案，均不在本书范围内。

## 5. 引用格式

| 类型 | 格式 | 示例 |
|---|---|---|
| 标准 | 标准号 + 名称（年份） | GB/T 2828.1《计数抽样检验程序 第 1 部分：按接收质量限（AQL）检索的逐批检验抽样计划》 |
| 法规 | 法律名称 + 条款号 | 《个人信息保护法》第五十二条（个人信息保护负责人） |
| 事故 | 发布主体 + 公告名称 + 日期 | 某云服务商《XX 地域服务中断说明》（20XX 年 XX 月）——主体名可保留，因为公告本身是公开的 |
| 研究 | 机构 + 报告名 + 年份 + 样本 | 某某研究院《XX 报告》（20XX），样本 N＝XXXX |

> **一条硬规则**：任何数字，如果只有「一个数」而没有「分母 + 时间窗 + 口径」，**不许进正文**。宁可写「数量级在万级」，也不写一个来路不明的精确值。

## 6. 公开来源总表

| 篇 | 来源 | 支撑什么判断 |
|---|---|---|
| 互联网 | Kubernetes 官方文档（requests/limits、探针） | 副本是期望值；readiness 与 liveness 职责；CFS 节流 |
| | 各云厂商公开故障公告与复盘 | 可用性断崖、重试风暴、发布与回滚 |
| | SRE 公开实践（SLI/SLO/错误预算） | 可用性不是唯一 SLI；错误预算是决策工具 |

| | Web Vitals 公开定义 | 性能预算先于选型 |
| 物联网 | MQTT 规范（OASIS） | QoS 是代价等级；离线与会话语义 |
| | 公开固件 OTA 事故与厂商安全公告 | 双分区与回滚的必要性 |
| | GB 50348《安全防范工程技术标准》、GB 50116《火灾自动报警系统设计规范》 | 物理安全；断电开锁与消防联动的优先级冲突 |
| | 公开器件停产通知与交期公告 | 生命周期风险、单颗料即单点 |
| 智能体 | 公开 Agent 架构论文与框架文档（ReAct、工具调用、记忆分层） | 链路步数、状态外置、记忆分层 |
| | MCP / A2A 等公开协议规范 | 工具描述、schema 校验、协作边界 |
| | OWASP 大模型与智能体应用风险清单 | 提示注入、越权工具调用、审计缺失 |
| | 公开 Agent 基准（AgentBench / SWE-bench / GAIA）及争议 | 单步评测与端到端评测的差别 |
| 安全 | NIST SP 800-57（密钥管理）、公开 KMS 文档 | 密钥生命周期、信封加密、轮换周期 |
| | OWASP Top 10 与公开越权案例 | 权限给多了才是常态、行级与字段级权限 |
| | SBOM 规范、公开供应链事件 | 依赖不可验证、第三方组件清单 |
| | 公开日志完整性要求 | 审计日志不可篡改与取证链 |
| 合规 | 《网络安全法》《数据安全法》《个人信息保护法》及配套规章 | 义务识别、效力层级、部门分工 |
| | GB/T 22239（等级保护基本要求）、GB/T 35273（个人信息安全规范） | 等保条款落到工程哪几条、个人信息处理规则 |
| | 《互联网信息服务算法推荐管理规定》《生成式人工智能服务管理暂行办法》 | 算法备案与生成式服务备案的触发条件 |
| **质量** | ISO 9000 族（质量术语）、ISO 9001（体系要求） | 缺陷来源分类；来料/过程/出货三段责任 |
| | PAF 质量成本模型（预防/鉴定/失败） | 质量成本四类；越晚发现越贵 |
| | GB/T 2828.1、公开 SPC 方法（Cp/Cpk/PPM） | 过程能力；AQL 不是允许不合格率 |
| | 公开可靠性指标定义（故障率/MTTR/MTBF） | 分母不同则数值不可比 |
| 测评 | GB/T 2828.1 / ISO 2859-1（抽样检验） | 设备侧判「批」的方法与成立前提 |
| | ISO/IEC 25010（系统与软件质量模型） | 软件侧判什么、覆盖率不在其中 |
| | ISO 19011（管理体系审核指南） | 供应商侧判「体系」而非「样品」 |
| | 公开等保测评报告制度与机构要求 | 报告有效期、不符合项、复测触发 |
| **商业化** | GB 50500《建设工程工程量清单计价规范》思路 | 报价拆分粒度与责任边界 |
| | 公开招投标文件与资格条款 | 认证/案例/财务如何成为投标门槛 |
| | 公开 SLA 定义、备件策略实践 | 承诺档位对应成本台阶 |
| | 公开模型计价文档、FinOps 实践 | Token 成本结构；按失败与重试核算 |

## 7. 禁用清单

以下内容一律不得进入书稿、演讲页、专栏：

- 任何公司内部数据：批次台数、通过率、失败台数、告警量、闭环率、维修单量、性能压测值
- 任何内部制度的运行情况：评审记录、验收结论、认证台账、影响评估记录、备案状态
- 任何内部口径冲突：同一指标的两套定义、两套评分权重、三处不一致的年限表述
- 客户名、楼盘名、供应商名、机构名（检测机构尤其不能出现）
- 芯片与模组型号、BOM 明细、物料单价、毛利率、报价单字段
- 未发布的产品规划、在研型号、测试中的功能
- 员工姓名、工号、内部花名
- 任何住户人脸、通行记录、抓拍图、门禁日志（示例一律重绘或抽象）

> **判定标准**：这段话如果被同行看到，他会不会问「这是你们公司吧」？会问，就删——不是改，是删。

## 8. 交稿前的来源自查

| # | 检查 | 不通过的表现 |
|---|---|---|
| 1 | 没有一处可被反推到具体公司 | 出现「我们」+ 具体数字；或城市 + 规模 + 时间三项中齐全两项 |
| 2 | 每个复合场景都标了构造说明 | 读起来像真实项目，却找不到「由 N 个公开案例重构」 |
| 3 | 每个数字都有标签与出处 | 正文里出现没有标签的精确值 |
| 4 | 每段推演都列了假设 | 只有结论没有假设，等于不可反驳 |
| 5 | 每条 A 级引用都能查到 | 只写「有研究表明」，没有机构与年份 |
| 6 | 没有一个判断依赖「内部经验」 | 出现「我们的经验是」「业内通常」——后者是套话，前者越界 |

### 60 条判断点配额（硬约束）

30 章 × 2 条 ＝ 60 条，收口章（31）只重述不新增。判断句可以来自 A/B/C 任一来源，但**不能来自内部经验**——这是配额之外的第二条硬约束。
